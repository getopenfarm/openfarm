# OpenFarm — Feature Plan

## Overview

OpenFarm is a print farm management webapp covering printers, filament, maintenance, parts, assemblies (BOMs), and print jobs. It's being built open-source-first and kept private for now, as a single-tenant, self-hosted app (one farm per install).

## Guiding principles

- **MVP-first, not data-model-first.** Ship a real, demoable capability as early as possible and let later phases extend it, rather than building the full schema before anything is usable. The previous version of this plan required filament tracking, printer profiles, and sliced files to all exist before a printer could even be added to the fleet — this version inverts that: fleet management and live Bambu Lab connectivity are the *first* thing built, because they're the most visible, most demoable capability and the Bambu local-MQTT integration path is well-understood, not R&D-risk territory (see Phase 1).
- **Ordered by day-to-day print-farm operational value, not just build convenience.** After Phase 1 (which is both a structural prerequisite for almost everything else *and* the single most-checked piece of information in a real farm), phases are sequenced by what an actual farm operator needs next in practice. Phase 2 (Profiles) is the one deliberate exception to "operational value first" — it's foundational plumbing rather than a visible day-to-day capability, pulled forward because a concrete acquisition path (slicer-bundle import) exists for it now, and because real sliced files and jobs later need real profiles under them rather than a throwaway stand-in. From Phase 3 onward the ordering resumes prioritizing operational and product value — not running out of filament mid-job, then a real parts catalog — ahead of internal permission hygiene (Phase 5) that doesn't affect daily operation. See Phases 2–5 below and the Dependency notes section for the reasoning.
- Usable by a solo operator or small farm without extra complexity getting in the way.
- Automation is *suggested*, not forced — a human still physically loads spools and parts, so the system should assist decisions rather than take them over.
- Every feature targets a self-hosted single-farm install.
- TDD is applied selectively, not uniformly: deterministic domain logic (state machines, BOM decomposition, filament weight math) gets red-green-refactor; orchestration-only application code, EF Core plumbing, the real Bambu MQTT client, and React components are test-after or fake/fixture-based instead. See Phase 1's sub-milestones for a concrete example of where this split falls.

## Phase groupings (for orientation only)

The structure below is intentionally flat — every phase is its own top-level section so any one of them can get a full detail/dev plan without dragging a dozen unrelated features along with it. These groupings are just informal labels for orientation, not a re-introduction of nested phases:

- **Foundation:** Phase 0
- **Core MVP:** Phases 1–11
- **Smart features & integrations:** Phases 12–18
- **Scale & extensibility:** Phases 20–24

## Dependency notes

**Core MVP (1–10) is ordered by a combination of demo-ability and real print-farm operational importance, not data-model completeness or internal build convenience:**
- **Phase 1** (Fleet management + live Bambu integration, including a live camera feed) is built first and deliberately ships *without* linking a profile record onto the printer entity — a printer's spec fields stay inlined directly on the printer entity. Phase 2 introduces a standalone machine-profile catalog (via slicer-bundle import) without wiring it onto `Printer` rows; that linkage — not the catalog's existence — is what stays deferred, until whichever later phase actually consumes it (Phase 4 — Part library, which folds in sliced-file records). Phase 1 is also the single structural prerequisite almost everything else in this plan depends on — every other phase either attaches to a printer row or reads its status history.
- **Phase 2** (Profiles — machine + filament, imported from slicer bundles) replaces the former minimal-print-flow phase outright rather than deferring it: a sliced file only means something once it's tied to a real machine/filament profile, so the next real print-trigger demo moment is the full Jobs phase (Phase 7) once parts/assemblies/sliced files exist under it, not an intermediate ad-hoc file push. Building Profiles this early also pulls forward what the old plan slated for Phase 4 (printer-profile extraction) and the whole of the old Phase 5 (Filament profiles) — justified now by slicer-bundle import being a concrete, immediate acquisition path for real profile data, not by duplication across multiple owned printers (the old Phase 4 trigger). Phase 5 keeps only tags/feed-config/RBAC now that profile extraction has moved here.
- **Phase 3** (Filament tracking) is ranked ahead of fleet hardening/RBAC for the same operational-value reason: a spool running out mid-print is the most common real-world failure a farm operator deals with day to day, and basic spool tracking (add/track/mark-finished) needs zero printer knowledge at all. The one exception is called out explicitly in Phase 3 itself: its *auto-reload* branch needs to know which feed slots are configured as auto-reload, and that field doesn't exist until Phase 5 — core filament tracking isn't blocked on Phase 5, only that one behavior is.
- **Phase 4** (Part library, with sliced files and in-app slicing folded in) is pulled forward ahead of fleet hardening/RBAC because it's real, user-visible product catalog work — parts an operator actually adds, browses, and manages the files of — rather than internal multi-user hygiene, and it needs zero printer knowledge (see the Phases 4 and 6 note below), so nothing in Phase 1's live-connector work gates it. Sliced-file formalization (originally its own phase) is folded in here rather than deferred, and this phase now also folds in the old plan's separate Phase 23 (In-app slicing) for the same reason: a part isn't demoable/job-ready until its nozzle diameter and material type are known, and automatic in-app slicing on upload derives that immediately rather than requiring an external manual slicer round-trip or a separate later phase — there's no reason to make either wait behind Fleet hardening (Phase 5) or Assembly (Phase 6). This primary compatibility match (nozzle diameter, generic material type — see the phase's own detail below) is either parsed straight from an already-sliced upload or derived from an in-app slice, needing no dependency on Phase 2 at all; only the optional narrower Filament Profile/color-variant override does.
- **Phase 5** (Fleet hardening + real RBAC) — tags, feed-config, and the real permission catalog — moves here specifically *because* it's multi-user hygiene rather than something a solo/small-farm operator needs to see working day to day, and now sits behind Part library for the same product-over-hygiene reason. It's real, necessary work, just not more urgent than Phases 2–4.
- **Phases 4 and 6** (Part library — including its folded-in sliced-file records and in-app slicing — and Assembly/BOM) need zero printer knowledge — no API, no file format, no live connection — beyond what Phase 2 optionally provides for a part's narrower Filament Profile/color-variant override, and can be built in parallel with or independently of Phase 5 (Fleet hardening + RBAC), which touches printers directly but doesn't block them.
- **Phase 6 (Assembly/BOM) must be complete before Phase 7 (Production runs, jobs & queue) starts** — an earlier revision of this plan swapped them, and this reverses that swap. Phase 7's demand model is built directly on BOM explosion, so a queue built first would either be a throwaway part-only queue or force the assembly tree to be retrofitted into a shipped job entity. Phase 6 stays pure definition (no printers, no execution) precisely so it can be finished and tested independently first.
- **Phases 7–8 split demand from execution, and that split is the product.** Phase 7 owns the model (runs → run lines → part requirements → print jobs) and dispatch; Phase 8 owns unit-level outcomes, the shortfall/requeue loop, and progress rollups. They're separate phases so the queue can ship and be used before yield tracking and blended progress are built, but 8 is not optional polish — without it a "completed" job carries no truthful count and no defect/failure attribution.
- **Phases 9–11** (Maintenance, Dashboard, Backup & restore) tie everything above together and stay last, same as the original plan.

**Filament spools still do not depend on a filament profile** (Phase 3 vs. Phase 2) — a spool can be added and tracked through in storage / using / finished with no profile attached; a profile is only required once the spool is actually used in a job.

**Smart features and scale phases carry the same dependencies they always did:**
- Phases 12–18 mostly depend only on their Phase 1–11 prerequisites (e.g. Phase 12 needs Phase 1's idle state and Phase 7's queue; Phase 18 needs the data capture that starts in Phase 1 and Phase 7).
- Phases 20–24 build on the swappable printer-connector boundary from Phase 1.

## Phase 0 — Foundation (prerequisite, not user-facing)

**Status: Delivered.** Implemented via `specs/001-foundation/` (spec, plan, tasks) — real JWT
login for the seeded operator, a `FarmSettings` singleton, encrypted/masked/immutable
connection secrets, the structural activity log, and the base shadcn UI kit are all live.
Phase 1 can now build on top of it.

Scoped down deliberately for the MVP-first pivot — each piece below is cut independently based on whether stubbing it is defensible or a corner that bites us later, not lumped into one all-or-nothing "foundation" block:

- **Auth: real, but coarse.** One seeded user, real JWT-based login, no self-registration, no role-management UI. A no-auth throwaway slice was considered and rejected — this system stores real Bambu printer access codes and the activity log needs a real actor, so retrofitting auth later would mean unwinding both.
- **Single-tenant.** One farm per install: no organization/tenant column anywhere. Farm-wide settings live in a single `FarmSettings` row.
- **RBAC: placeholder policy shim now, real catalog in Phase 5.** A thin permission-shaped policy attribute is added to endpoints from the start (so it doesn't need retrofitting later), but its handler just checks "authenticated" until Phase 5 swaps in the real seeded permission catalog and four roles (Owner/Admin/Operator/Viewer, Operator/Viewer optionally scoped to printer tags — see Phase 5).
- **Connection secrets: real encryption from day one, not stubbed.** These rows hold a real physical printer's LAN access code — a working credential, not a demo fixture. Encrypted at rest using ASP.NET Core's `IDataProtector` (no external KMS needed for self-host) from the first commit.
- **Activity log: built for real.** A generic, polymorphic activity log (entity, event type, actor, timestamp) underlies every status change from the start — this is what Phase 1's printer status-change logging and Phase 18's analytics both read from, and it needs to start accumulating from day one rather than being bolted on retroactively.

## Phase 1 — Fleet management + live Bambu integration

**The first feature built after the scaffold.** Combines what the previous plan split across "Fleet management," "Live printer integration," and "Camera / live monitoring" into one phase, because the whole point of building fleet management first is to make it live and visible from the start rather than a static CRUD screen that gets live status (and, later, video) bolted on much later.

- Printer entity with spec fields **inlined directly** (name, model, IP address, serial number, connection-secret reference) — no separate printer-profiles table yet, and no link onto one either (see Dependency notes above; Phase 2 builds a standalone machine-profile catalog, not yet wired onto this entity).
- Printer status modeled as an explicit domain state machine: `Idle` / `Printing` / `AwaitingClear`, split into two operations — a strict `TransitionTo` for human-initiated commands (e.g. "Mark ready") that throws on an illegal manual jump, and a lenient `ObserveStatus` for connector-reported physical reality, which reconciles and logs rather than rejecting a fact the printer is already doing (e.g. someone started a print from the Bambu app directly). `Offline`/connectivity is tracked separately as connector connection state, not as a `PrinterStatus` member. `Maintenance` is deferred until Phase 9 exists to enter it.
- `IPrinterConnector` interface, with a `FakePrinterConnector` so application code and UI can be built and tested well before the real connector is finished.
- A real `BambuLanConnector` over MQTTnet, connecting to Bambu X1/P1/A1-series printers in LAN-only + Developer Mode: MQTT over TLS on port 8883 (topic `device/<serial>/report` for status/telemetry/AMS-slot pushes), validated against a physical printer.
- SignalR push (`/hubs/farm`) into a minimal fleet-list + printer-detail UI — status/telemetry updates live without a page refresh.
- A minimal live camera view on the printer-detail page (RTSP-ish stream on port 322 for X1/H2/P2, port 6000 for P1/A1) — folded in here rather than left until the old Phase 26, since it reuses the exact same LAN connection/connector boundary and adds a much more visceral "it's really working" demo moment for close to no extra cost. Recording/timelapse linkage stays a later phase (see Phase 24).
- **Scope for this phase's demo bar: live monitoring only** (status, telemetry, AMS slots, camera feed). No print-trigger or file push yet — that's Phase 7 (Jobs). The goal here is "watch the fleet update live off a real printer," not "make it do something."
- Every status change and connector reconciliation is logged via the Phase 0 activity log.

### Sub-milestones for this phase

Sequencing logic: a small throwaway hardware spike first (de-risks the one genuinely uncertain element — the real Bambu MQTT protocol — before committing to interface shape), then a thin vertical slice (visible CRUD before the real connector, real connector before real-time push) rather than a full backend-then-UI build-out.

- **M0.0 — Add reverse-engineered Bambu API reference as a git submodule.** The user has already gathered multiple sources of reverse-engineered Bambu Lab API documentation/code (protocol details, message shapes, MQTT/FTP/camera behavior across models) from prior investigation, published at [tanghq33/bambulab-api-docs](https://github.com/tanghq33/bambulab-api-docs) (`develop` branch). This is added as a git submodule at `third_party/printers/bambulab/` and used as the primary protocol reference — supersedes/supplements the public community projects noted below. `third_party/printers/<brand>/` is the standing convention for this kind of reference material, so a future brand (see Phase 15 — Expanded live printer integration) gets its own sibling directory without touching this one.
  For context, public prior art confirming this integration path is well-trodden (not R&D-risk territory): [Bambu.NET](https://github.com/ColdThunder11/Bambu.NET) (MQTTnet-based `BambuMQTTClient`, closest match to this project's C#/.NET stack), [BambuSharp](https://libraries.io/nuget/BambuSharp) (NuGet, wraps temps/progress/AMS state), and [bambulabs_api](https://pypi.org/project/bambulabs-api/) (Python, documents MQTT/FTP/camera behavior in detail even though it's a different language).
- **M0.1 — Bambu MQTT spike (throwaway, no product code).** Raw MQTTnet client against the physical printer in LAN-only + Developer Mode: TLS connect on 8883, subscribe `device/<serial>/report`, dump raw JSON. Cross-reference against the M0.0 submodule's documented message shapes. Capture real fixture payloads for M0.5's tests.
- **M0.2 — Minimal-but-real plumbing.** Seeded user + JWT login, `FarmSettings` singleton, `connection_secrets` table with real `IDataProtector` encryption, `activity_log` table + FastEndpoints post-processor proven against one dummy mutation.
- **M0.3 — Printer domain + CRUD (no live connector yet).** `Printer` entity, `PrinterStatus` state machine — **TDD**: `TransitionTo` + `ObserveStatus`, all transition pairs, invalid-transition exceptions, reconciliation/logging behavior on a physical-reality mismatch. FluentValidation, FastEndpoints CRUD endpoints, EF Core migration.
- **M0.4 — Minimal UI.** Fleet list + add-printer form (react-hook-form + zod) + detail/status view, wired to the real Orval-generated client. Plain TanStack Query polling — no SignalR yet.
- **M0.5 — Real `BambuLanConnector`.** Built from M0.1's fixtures behind `IPrinterConnector`, developed against `FakePrinterConnector` first. **Test-after / fake-based**: fixture-replay unit tests (real captured JSON → parsed telemetry/AMS-slot model), in-process MQTT broker tests for subscribe/publish wiring. **Manual verification only, not in CI:** final validation against the physical printer — TLS handshake, reconnect-after-drop, AMS accuracy.
- **M0.6 — SignalR live wiring.** `/hubs/farm` pushes status/telemetry, frontend subscribes into the TanStack Query cache — the actual demo moment: the fleet page updates live off a real printer.
- **M0.7 — Minimal live camera view.** Render the printer's local video stream (port 322 or 6000, per model) on the printer-detail page — no recording/timelapse yet (see Phase 24).

### Risks/notes

- Enabling LAN-only + Developer Mode disconnects the printer from Bambu Cloud/the official app while active — a real workflow disruption during development, not just a footnote, since it's the user's own physical printer.
- Local MQTT access is Bambu-permitted but unofficial/unversioned — firmware updates have previously altered third-party access in the past. This is an ongoing maintenance risk for `BambuLanConnector`, not a one-time cost.
- Camera/live-video port differs by printer generation (322 for X1/H2/P2, 6000 for P1/A1); FTPS file transfer runs on port 990 and becomes relevant in Phase 7 — Production runs, jobs & print queue, not this phase.

## Phase 2 — Profiles (machine + filament, imported from slicer bundles)

- Two standalone catalogs: **machine profiles** (nozzle size, bed volume, enclosure, supported materials, whether the model supports live integration — the fields originally slated for the old plan's Phase 4 `printer_profiles` extraction) and **filament profiles** (material, brand, color, tuned settings; schema kept close to Spoolman's shape, consistent with Phase 3's filament modeling — see Phase 14 — Spoolman-compatible filament API).
- Import flow: the user uploads a slicer bundle — an OrcaSlicer profile-bundle `.zip` (individual printer/filament preset JSON files) or a Bambu Studio project/preset export (a `.3mf`, itself a zip container, or Bambu's own preset bundle). The backend extracts the bundle and parses whichever machine and filament presets it finds, then presents them to the user as a **selection list** rather than importing everything blindly — a bundle commonly contains multiple presets (e.g. several filament colors), and the user picks which ones to keep.
- Base/override preset relationships present in the source bundle (OrcaSlicer/Bambu Studio's own inheritance model — e.g. a color-specific filament preset overriding a shared base) are preserved as a parent/child relationship in OpenFarm's schema, rather than flattened into independent copies.
- Imported profiles are a standalone library in this phase — not yet linked to a specific fleet `Printer` row (Phase 1) or consumed by a job. That linkage happens naturally once Phase 4 (Part library, which folds in sliced-file records) and Phase 7 (Jobs) need to reference a specific machine/filament profile.
- Structured per-field manual create/edit forms are explicitly out of scope for this phase's MVP — profiles exist only via import. Once imported, a profile's raw data can be viewed and overridden through a **JSON editor/viewer** rather than dedicated form fields; purpose-built forms per profile attribute are a deliberately deferred follow-on once real imported data has settled the schema.
- No live printer connection needed — pure file-parsing + catalog CRUD, the same "zero printer knowledge required" property Phase 4 (Part library) has.

## Phase 3 — Filament tracking

- Ranked ahead of fleet hardening/RBAC (Phase 5) for the same operational-value reason as Phase 2: a spool running out mid-print is the single most common daily operational failure on a real print farm, and the core lifecycle below needs zero printer knowledge. **One explicit exception:** the auto-reload branch needs to know which feed slot is configured as auto-reload, and that configuration field doesn't exist until Phase 5 — everything else in this phase works today, only that one behavior activates once Phase 5 lands.
- Spool tracking never requires a physical barcode/unique ID — an optional identifier can be added later for anyone who wants to scan spools, but it's never required to use the feature (see Phase 13 — Optional spool identification).
- Each spool has three states: **in storage** (not loaded), **using** (loaded onto a feed slot, actively tracked), and **finished** (depleted). Remaining weight is visible at the moment a spool is removed, so the operator can decide immediately whether it goes back to storage (still has usable filament) or gets marked finished — no in-between holding state needed.
- Remaining weight is estimated automatically from job usage while a spool is in use.
- For single-spool and AMS slots: marking a spool finished stays a manual action. A slot running out doesn't auto-continue, so the operator is already there physically replacing it — and pulling a spool doesn't always mean it's empty (could be a deliberate color change).
- For auto-reload slots (see the exception noted above, once Phase 5's feed-config field exists): running out is exactly the moment the device is built to react to, so the system can detect it directly from the numbers — once cumulative job usage catches up to a spool's starting weight, mark it finished and flip the active slot to the standby spool automatically, without waiting on a manual mark. This is still an estimate rather than a precise measurement, so a manual override should stay available in case actual usage drifts from it over time.
- Before flipping to the standby spool, the system checks that its assigned filament profile matches the job's required material and color. A mismatch doesn't pause the swap — the entire point of auto-reload is continuing unattended — but it raises a dashboard warning and, once notifications exist (see Phase 17 — Notifications), an alert, and the mismatch is logged against the job so it's traceable afterward rather than silent.
- Internally modeled with a schema deliberately close to Spoolman's (spool / filament / vendor), even though this data lives natively in OpenFarm rather than depending on a separate Spoolman instance — see Phase 14 — Spoolman-compatible filament API for why.
- **No printer knowledge required** for the core lifecycle. Everything above (except the noted auto-reload exception) works identically regardless of which printer brand or model eventually loads the spool.

## Phase 4 — Part library (with sliced files and in-app slicing)

- Add parts with a name, an *optional* Filament when the file needs slicing (a generic material like "Any PETG," a specific filament variant, or nothing at all — see the "any material" note below), and **exactly one file** (STL, 3MF, or G-code) — a part never holds more than one file at a time; Assembly (Phase 6) is the mechanism for combining multiple distinct parts, so a Part itself stays deliberately atomic. A part is only ever saved once fully described — **there is no manual-entry fallback anywhere**: not for nozzle diameter, material type, print-time/weight estimate, or thumbnail. If a file can't be parsed or sliced, or no printer with a known nozzle diameter is registered yet, the add/replace is rejected outright rather than saved incomplete. **Filament-diameter matching is dropped entirely** — the desktop-printer market this project targets is virtually uniform at 1.75mm, and printer telemetry doesn't expose it anyway.
- **A requires-slicing file added with no Filament specified defaults to "any material," not a rejection.** The system still runs its own immediate in-app slice — needed regardless, since a part is never saved incomplete — against a fixed, internal, non-operator-configurable generic default material used solely to produce that immediate estimate/nozzle-diameter/thumbnail; the saved part's filament requirement is then recorded as fully unconstrained (matches any spool of any material), broader than "any PETG" (which still requires PETG specifically). This is a deliberate, named accuracy tradeoff — the estimate is a best-effort approximation, not guaranteed accurate for whatever material the part is eventually printed in once matched to a real job (Phase 7) — traded off against the friction of forcing every STL upload to commit to a material before the operator necessarily knows or cares which one it'll end up using. The operator can always avoid this path by specifying a real Filament up front, or narrow an "any material" part to a specific Filament Profile/color-variant later at the same review/confirm step every other requirement uses. This does not extend to an already-sliced file — its process parameters are physically fixed to one material once sliced, so "any material" is never valid there.
- There is no separate "source model" concept — a part's one file is simply determined, at upload, to either **require slicing** (an STL, or a 3MF without embedded sliced G-code) or **not require slicing** (a G-code file, or a 3MF that already contains sliced G-code/toolpath data). Sliced-file formalization is folded into this phase rather than deferred to a later one, and this phase now also folds in the old plan's separate Phase 23 (In-app slicing) for the same reason: a file requiring slicing carries none of the parseable time/weight/nozzle metadata an already-sliced file does — only an actual slicing pass produces it.
- **Automatic in-app slicing never persists a sliced-output file, and a successful slice is reviewed before it's saved.** Uploading a file that requires slicing automatically runs it through a headless slicer engine (OrcaSlicer by default; Bambu Studio also supported; configurable in farm settings — the *only* farm-level slicing setting) against the specified Filament and **whichever nozzle diameter is most common among the farm's currently-registered printers** (auto-detected, no farm setting or operator input for this), deriving nozzle diameter, generic material type, a parsed print-time/weight estimate, and a rendered thumbnail — the slicer's actual output is discarded, and the part's file remains exactly the STL/3MF as uploaded. A successful slice lands in a **"ready for review"** state rather than saving directly: the operator sees the derived data, may attach or change a narrower Filament Profile/color-variant override now that a real result exists to narrow, then either confirms (saving the part immediately from the already-derived data) or discards it (nothing saved). None of this reopens *what* gets derived or lets the operator hand-edit the derived numbers — it only gates *whether* a successful result is committed. If no printer with a known nozzle diameter is registered yet, slicing has nothing to target and the add/replace is rejected outright, with no review state ever reached. Manually uploading an already-sliced file (G-code, or a 3MF that already contains one) is the one path where the file itself is retained and parsed in place, with its thumbnail extracted from its own embedded preview image (a standard slicer/firmware convention) — as a part's only file when no original model is available at all (e.g. a downloaded G-code), or as a replacement. **This review/confirm step applies uniformly to every file type, not only a slicer-derived result** — an already-sliced file's add/replace goes through the identical submit → processing → ready-for-review → confirm/discard shape, it just typically resolves near-instantly since reading embedded metadata needs no external process the way slicing does; there is no longer a separate one-step synchronous path for it. **Attaching the file (plus a Filament pick, if needed) kicks off processing immediately, as one continuous add-part experience** — the operator keeps entering/editing the part's name and tags in the same dialog while processing runs in the background; only the confirm/save action itself is gated on processing having reached "ready for review" (and, for a new part, a name having been entered).
- **A part's filament requirement is a collection, not a single value**, so a real multi-color/AMS part is representable: an already-sliced file is scanned across every plate and every AMS slot within each for its detected material + color, and the results are **grouped by distinct (material type, color) pairs** — one filament requirement per distinct pair, not one per slot/plate, so e.g. two plates that are both black PETG collapse into a single requirement rather than duplicating. Each requirement is independently narrowable to an exact Filament Profile/color-variant, applying uniformly to every plate/slot sharing its pair. In-app slicing itself still only ever targets one operator-specified Filament (true multi-material *slicing* — assigning different materials to different regions of one model — is out of scope for this phase), so a part produced via automatic slicing always ends up with exactly one requirement even though the underlying data shape supports more.
- **There is no "job-ready" concept.** Every part that exists in the catalog is, by construction, fully valid and usable — nozzle diameter, material type, and an estimate are always present. The only status distinction a part carries is whether its file requires slicing (Phase 7 will need to slice it again for real toolpath data at job-dispatch time, since nothing sliceable was kept) or was already sliced on upload (its stored file can be sent to a printer directly).
- Uploading a new file for an existing part is always a **direct replacement** of its current one — never additive, and it either fully succeeds (file, thumbnail, and derived data all update together) or changes nothing at all if the new file fails to process. Running the same design against a different nozzle-diameter/material target means either replacing the file and re-slicing (discarding the previous variant) or creating a separate Part record for that variant; a Part never holds multiple simultaneous variants of itself.
- A part's compatibility match is **printer- and material-agnostic by default**: nozzle diameter and generic material type (e.g. "PETG") — parsed directly from an already-sliced upload, or derived from an in-app slice — are used as its baseline match, with any printer sharing the nozzle diameter, and any spool/filament of that generic material, qualifying, with **no concept of linking a part to a specific Machine Profile**. An operator can optionally narrow the material match to an exact Filament Profile/color-variant (Phase 2/3) — e.g. a Bambu multi-color 3MF's baked-in AMS slot-to-color mapping.
- A 3MF that happens to bundle multiple plates/objects is treated as one indivisible file belonging to one part, using only the first plate's image for the thumbnail, and is never split into multiple parts. **Filament-requirement detection does scan every plate**, however (grouped by distinct material+color pair, as above) — a genuine reopening of what was originally a blanket "no multi-plate handling at all" limitation, scoped specifically to filament requirements; a part's estimated print time/weight become the sum across all plates accordingly, since a multi-plate file prints them all as one continuous job.
- Tag parts (category, product line, etc.).
- A part's derived compatibility data needs no additional dependency on Phase 2's profile catalog beyond the required Filament itself; Phase 2 is only additionally needed for the optional narrower Filament Profile/color-variant override.
- **This phase is "whichever later phase actually consumes it"** referenced in Phase 1's own dependency note above: it finally wires the Printer ↔ Machine Profile link Phase 1/2 deliberately left deferred, reading a printer's nozzle diameter from its linked Machine Profile (which already models nozzle size) rather than a new duplicate field on `Printer`. The link is optional at printer-creation time (a matching Machine Profile might not be imported yet) — a printer can exist unlinked, it just doesn't count as a "real fleet member" for this phase's nozzle-diameter auto-detection (FR-005a/FR-005b in `specs/007-part-library/spec.md`).
- In-app slicing (engine + a file requiring slicing + a target material and auto-detected nozzle diameter → derived data + thumbnail, no persisted output) is built as a reusable capability, so Phase 7 (Jobs) can later invoke it on-demand at job-dispatch time to produce actual sliceable output for a job's exact target printer, without rebuilding the integration — this phase itself only wires up the automatic-at-upload, derive-only trigger; job-dispatch-time slicing is Phase 7's to build once a Job entity exists. Real job/printer matching at that later dispatch time depends on which printers and feed-slot materials are actually available then — a separate, dynamic concern from this phase's one-time, auto-detected slicing target.
- **No live printer connection required.** A part's file (whether requiring slicing, automatically sliced, or manually uploaded) and derived data are all catalog/slicing-pipeline data — no live printer *connection* needed, though nozzle-diameter auto-detection does read the printer catalog; only *using* an already-sliced file in a job (Phase 7) involves an actual printer.

## Phase 5 — Fleet hardening + real RBAC

- Printer tags (location, capability, farm zone, etc.) — the same tags double as scoping for Operator/Viewer roles and, later, circuit grouping (see Phase 12 — Intelligent queue matching).
- Feed configuration field: single spool, AMS, auto-reload/splicer, or a combination — this is what unblocks Phase 3's auto-reload branch, noted there as a deliberate forward dependency.
- `AwaitingClear` UX polish: a finished/failed/cancelled job leaves its printer in awaiting clear, not idle. A quick, explicit "Mark ready" action moves it to idle, which is the only state a printer can be assigned a new job from or picked up by a queue-matching suggestion. This is the state machine's `TransitionTo` path built in Phase 1.
- Swap Phase 0's placeholder permission shim for the real seeded permission catalog + four roles (Owner/Admin/Operator/Viewer); Operator and Viewer can optionally be scoped to specific printer tags rather than the whole farm.

## Phase 6 — Assembly (BOM)

**Definition layer only — no execution, no printers, no in-flight quantities.** An Assembly describes what a finished product is made of; *producing* one is Phase 7's job. This phase sits ahead of Jobs (reversing an earlier swap) because Phase 7's entire demand model is built on exploding a BOM — building the queue first would mean either shipping a throwaway part-only queue or retrofitting the assembly tree into an already-shipped job entity. Phase 6 stays pure definition (no printers, no execution) precisely so it can be finished and tested independently first.

- Build assemblies from multiple parts plus quantities. Support nested assemblies (an assembly can include other assemblies as sub-components) to arbitrary depth.
- **BOM lines are polymorphic**: a line targets a Part, a sub-Assembly, or a **non-printed component** (screws, heat-set inserts, magnets, bearings, packaging). Non-printed components are modeled now — name, whole-piece quantity per assembly (unitless), optional cost per piece — but carry **no stock tracking and never gate anything**. They exist so a BOM is a truthful description of the product, and so cost-per-assembly (Phase 18 — Analytics dashboard) isn't filament-only. Making the line polymorphic later would mean migrating every existing BOM row; scoping it to informational-only keeps the cost near zero now.
- **BOM explosion is a pure, deterministic function** (assembly + quantity → flat part quantities) and is the clearest TDD target in the plan: nested depth, a part appearing at multiple depths, quantity multiplication down the tree, cycle detection (an assembly that transitively contains itself is rejected at save time, not at explosion time), and a maximum nesting depth.
- Explosion **aggregates by part**, summing across every path a part appears on, and retains the per-path breakdown as display-only metadata ("6 knobs: 2 direct + 4 via the handle sub-assembly"). Phase 7 consumes the aggregate; the breakdown is only ever shown, never used for matching. **Accepted consequence:** progress attributed to a *nested sub-assembly* is prorated from its parent line rather than measured, since produced units aren't tracked per path. Accurate at the line level, approximate one level down.
- **Buildable units** — removed (2026-10-16). It was `floor(min over printed components of (good quantity ÷ quantity per assembly))` over hand-typed good quantities; it returns only once real stock/good-quantity data exists to feed it.
- No printer knowledge, no live connection, no file handling — the same "zero printer knowledge required" property Phase 4 has.

## Phase 7 — Production runs, jobs & print queue

**Two permanently separate layers.** *Demand* — what someone wants made — is hierarchical, snapshotted at creation, and never dispatched. *Execution* — what a printer actually does — is flat and atomic: one file revision, one target quantity, and one printer once dispatched. Printers print parts, not assemblies, so a BOM always explodes; the failure mode in existing print-farm software is throwing the tree away *after* exploding it, leaving nothing for progress to roll back into. OpenFarm keeps both layers, and that split is what makes assembly-level and run-level progress possible at all.

- Entities introduced here: `ProductionRun` (container — name, due date, priority, status, notes; later a source order from Phase 16 — Order integration), `RunLine` (one demanded thing: a Part *or* an Assembly, plus quantity), `PartRequirement` (exploded leaf demand), and `PrintJob` (the execution unit). Unit-level outcomes and progress rollups are Phase 8.
- **Every job belongs to a run; an unnamed run is simply one nobody bothered to name.** Queueing parts or assemblies directly creates a run with no name. The queue list hides the run framing — the row is labeled from its contents ("Bracket ×20", or "3 parts — bracket, knob, base") rather than showing an empty name or the literal string "unnamed run", which reads like a bug — but opening it reaches the **identical detail view a named run gets**, with lines, requirements, jobs, and progress all present. Naming a run later just sets the field: no conversion, no second entity, no separate "quick print" screen to build and maintain. One code path, one progress algorithm, and a solo operator never has to learn the concept to use the queue.
- **Grouping follows the operator's action, not a guess.** Several parts selected and queued in one action become one unnamed run; the same parts queued one at a time become separate runs.
- **Requirement grain is per (run line, part)**, with quantities summed across every BOM path within that line. Both alternatives were rejected for concrete reasons: *per-run* grain (one row per part across the whole run) makes assembly progress uncomputable as soon as two lines share a part, since there's no way to tell whose units you have; *per-BOM-path* grain forces one plate's output to be split across multiple rows, which reintroduces an allocation ledger. Per-line grain lets a job point at exactly one requirement through a plain foreign key.
- **Accepted cost of that grain: two run lines needing the same part print separately.** Line A needing 20 brackets and Line B needing 15 produce two requirements and two job sets, and therefore more plates than a pooled scheme would. This is deliberate — OpenFarm's job is to *produce*, not to manage inventory — and cross-run pooling only pays off alongside a stock ledger, which is explicitly out of scope (see Out of scope).
- **The BOM explosion is snapshotted at run creation**, exactly as a job snapshots its sliced file. Editing an assembly's BOM afterwards never alters an in-flight run.
- `units_per_print` on the Part entity — **a small amendment to Phase 4's part record** — defaulting to 1, auto-suggested from a sliced file's per-plate object count where parseable, and operator-overridable. Without it every quantity in the system is wrong for anyone running batch plates: a demand of 40 with a 4-up plate is 10 print runs, not 40. This is the one operator-editable field on a Part that isn't slicer-derived — a deliberately narrow exception to Phase 4's "no manual-entry fallback anywhere" rule, justified because it's quantity semantics rather than derived print data.
- Jobs are created in **whole plates** — `ceil(required ÷ units_per_print)` — so over-production is unavoidable physical reality, not a modeling choice. The rule: **record what actually came off the printer, satisfy what was required, cap progress at 100%, and forget the difference.** A requirement of 5 filled by a plate of 8 is complete, and nothing tracks where the extra 3 went. Recording the true 8 rather than clamping to 5 still matters, because Phase 8's defect and failure rates would otherwise be computed against a fabricated denominator.
- Quantity can also be **unlimited** — a standing line that keeps producing rather than completing once a target count is hit, e.g. an evergreen part a printer falls back to whenever otherwise idle. **Unlimited lines are not queue members.** They live in a separate **backfill tier** the dispatcher only consults when no finite job can be assigned to a given printer right now. Without that separation an unlimited line sits at the head of the queue permanently and starves everything behind it — a starvation bug, distinct from the ordinary capacity constraint that any running job imposes on its own printer. **Backfill carries two properties, not one:** it removes the re-queuing chore for a farm that perpetually prints the same parts, *and* it never displaces real demand. A large finite quantity (queue 999) delivers only the first — it still competes for queue position against actual orders. Both options exist deliberately and mean different things: use a finite quantity when the part should compete, backfill when it should only fill gaps. Paired with automated bed ejection (see Open decisions), backfill is also the path to genuinely unattended operation.
- Backfill rules: dispatch **one plate at a time**, re-evaluated at every bed clear, so the longest a newly-queued finite job can wait behind backfill is one plate's duration — bounded and predictable rather than indefinite. A configurable cap on how many printers a single backfill line may occupy simultaneously (default 1) stops one broad-matching evergreen part from claiming the entire farm the moment the queue drains. An optional cumulative-unit ceiling pauses the line rather than quietly producing thousands over a slow month. An unlimited line has no completion percentage, only cumulative counts. Note that backfill gets no exemption from the `AwaitingClear` → "Mark ready" gate (Phase 5) — a full bed physically blocks the next print regardless of tier. Slow bed-clearing throttles every job equally; it's simply most *visible* on backfill, since backfill is the thing meant to soak up idle time.
- **Two assignment modes, chosen per job.** *Unassigned* (the default) leaves the job in a pool and binds a printer at dispatch, matched on tags, nozzle diameter, loaded material and color, and availability. *Pinned* targets one specific machine because the operator has a reason to. A pinned job **never falls back to auto-matching** — that's the point of pinning — so if its machine is offline, in maintenance, or awaiting clear, the job simply waits, and is flagged in the queue as blocked on that machine rather than sitting silently stuck. Binding at dispatch rather than at creation is what keeps a job rescuable when a printer goes down, and is what gives Phase 12 — Intelligent queue matching anything to optimize over.
- **Queue order is manual and top-to-bottom.** The operator arranges the queue; the dispatcher takes the topmost job that a currently-idle printer can satisfy. No due-date or priority scheduling in this phase — due dates on a run are display metadata, not a scheduling input. This is deliberately dumber than a priority system and far easier to reason about when something is printing in an order the operator didn't expect.
- **The job is chosen by queue position; the printer is chosen by attribute match.** Among printers that satisfy the job, prefer the *least capable* one that still qualifies, so versatile machines stay free for jobs that need them. This is a cheap tie-break rather than real optimization — whole-queue optimization is Phase 12.
- **Snapshot vs. follow-latest is an explicit operator choice made when queueing**, not an internal rule the system applies on the operator's behalf. Both modes are offered on every line — the only thing "unlimited" changes is the default (**follow-latest on for unlimited lines, snapshot on for finite ones**). Exposing the choice everywhere is what lets one queue serve a job shop pinning an approved revision for a customer order and a farm iterating on an evergreen part, without either mode being a special case.
  - **Snapshot** — the part's revision is pinned at queue time; every plate in the line prints that revision, even if the part's file is replaced afterwards.
  - **Follow latest** — the part's current revision is resolved at each *plate dispatch*. A running job always keeps what it started with; nothing ever swaps mid-print. Because backfill already dispatches one plate at a time and re-evaluates at every bed clear, this costs almost nothing to hook in.
- **Both modes are the same mechanism at different times**, which keeps the implementation small: a job stores one revision identifier either way — pinned at queue time or resolved at dispatch — and the file store is **content-addressed by that revision hash**, so many jobs against one revision share bytes rather than each holding a copy. At farm scale that's the difference between a hundred jobs against a 200MB 3MF costing 200MB or 20GB.
- **The toggle stays editable after queueing.** It only ever affects the next plate, never a running one, so freezing it buys nothing: an operator who queued 200 under snapshot and then fixes a genuine defect in the model can flip to follow-latest mid-run instead of cancelling and re-queuing.
- Each new plate re-validates nozzle diameter and material against its target printer and loaded spool, so a replacement file needing a different setup is flagged rather than silently printed wrong.
- **A follow-latest finite line can print mixed revisions within one requirement.** Plates dispatched before and after a file change print different things, so a run's 200 units aren't necessarily homogeneous. This is the honest consequence of what the operator chose rather than a defect, it's fully traceable because every job records its revision, and Phase 8 surfaces "this run spans 2 revisions" rather than pretending otherwise.
- **Every job records which file revision it printed.** Phase 4 makes file replacement destructive ("never additive"), so nothing today distinguishes one revision from the next — a content hash plus an incrementing revision counter on the Part is enough, and is **the second small amendment to Phase 4's part record** after `units_per_print`. Without it neither mode above is implementable, and Phase 8's yield data becomes unexplainable the moment a file changes: defect rate jumps and nothing can attribute it to a revision. With it, defect rate is reportable *per revision*, which answers whether a tweak actually helped. Full version history is not implied and stays out of scope.
- Creating a run requires nothing beyond its parts existing — every part in the catalog already has real nozzle diameter and generic material type by construction (Phase 4 never saves an incomplete part), so there's no separate "is this part ready" gate. Sending a job to a printer is where the file-origin distinction bites: if the part's file was uploaded already-sliced, its stored file is sent directly; if it still requires slicing, Phase 4's reusable in-app-slicing capability is invoked on-demand at dispatch time to produce real toolpath data for that job's exact target printer. That on-demand slice is scoped to the job and never stored as the part's new file. A queued job whose part's nozzle diameter or material doesn't match the target printer/spool is flagged clearly rather than blocking creation.
- Job status workflow: queued → printing → paused → failed → completed → cancelled. Reaching completed, failed, or cancelled moves the printer to **awaiting clear** rather than idle (see Phase 1 — Fleet management + live Bambu integration) — the queue only offers a printer its next job once it's back to idle.
- **Run status: active → complete → closed**, plus cancelled. A run goes complete when every requirement is satisfied, but completion is **not terminal** — see Phase 8, where defects logged after the fact can reopen it. **Closed** is the terminal state that stops it reopening (see Open decisions for how it's reached).
- **A named run asks for confirmation before completing.** When the last job of a *named* run finishes and the operator hits Mark ready, they're asked to confirm the run is genuinely done rather than having it silently flip to complete. Unnamed runs skip this entirely — a one-part quick print doesn't need a ceremony.
- **Cancelling or deleting a *run* stops nothing physical by default.** Queued, undispatched jobs are cancelled; a job already printing when its run is cancelled keeps printing — a bulk, multi-job action never force-stops physical prints across the fleet as an automatic side effect, so cancelling a large run can't accidentally kill several machines' work at once. Jobs that were running when the run was cancelled still record their outcomes and filament usage, so yield and cost history stay complete rather than developing a hole. **An individual *job*, in contrast, can be explicitly paused, resumed, or cancelled (stopped) while printing**, for a printer with live integration — a single, deliberate, single-target action taken from the queue itself, distinct from the bulk run-level cascade above. (Revision: the original version of this phase stated OpenFarm would *never* send a stop command on the operator's behalf, reasoning that a remotely-killed print wastes the filament already laid down and the operator standing at the machine judges better. That blanket rule is superseded for the single-job case — real queue-level pause/resume/stop control was judged worth the tradeoff — but the underlying safety concern still shapes the design: a command is only ever a *request*, and the job's recorded status changes only once live telemetry confirms the printer actually reached that state, never optimistically on send, so a dropped or unacknowledged command can't leave OpenFarm's own records out of sync with the physical machine.)
- **Jobs are created eagerly for finite lines, lazily for backfill.** A 40-unit demand at 4-up creates all ten plate-jobs upfront, so the queue is fully visible and browsable and Phase 12 has real rows to optimize over. Backfill stays one plate at a time by design, created at dispatch.
- **Actual print duration is recorded per job**, alongside the estimate. The connector already knows start and end, it costs nothing to capture, and it's what later lets estimates be calibrated against reality and feeds printer utilization in Phase 18 — Analytics dashboard. Capturing it from the start matters because it can't be reconstructed retroactively.
- Unlimited queue depth that stays fast to browse as it grows.
- **A job's filament requirement is a collection, not a single value**, matching the shape Phase 4 already gives a Part: one entry per distinct (material, color) pair, so a multi-color AMS part is representable end to end. Defaulted from the part and overridable per job. A single-material part simply has a one-entry collection.
- For connected Bambu printers, live integration can auto-detect job start/finish using the same status-observation machinery Phase 1 built, and sending a job pushes the matched sliced file to the printer directly; the operator can also pause, resume, or cancel (stop) that job remotely once it's printing, with the recorded status only changing once telemetry confirms the printer actually reached that state (see the revised note above). Other brands have none of this — the operator retrieves the sliced file (e.g. via USB/SD) and starts the print manually, then marks it in progress, and pause/resume/cancel-while-printing for those is likewise a manual, self-reported status update rather than a real command, since there's no connection to send one over — Phase 15 — Expanded live printer integration extends automatic push, detection, and remote control to those brands too.
- Filament consumed by a job is recorded as a breakdown per spool/profile rather than a single total — a multi-color AMS job might draw from three different spools, and usage analytics later need to attribute grams to the right material and color. **Filament is attributed to failed units too:** a print that dies at 70% still consumed 70% of its filament, and recording only successful output would make cost-per-part and scrap cost systematically optimistic in Phase 18.

## Phase 8 — Progress, outcomes & yield tracking

Split out from Phase 7 so the queue can ship and be used while unit-level outcome granularity and rollups are built. Phase 7 alone gives a job a coarse completed/failed status; this phase makes it truthful, and turns the demand tree into the progress reporting that's the whole reason for keeping it.

- **A job closes with a set of outcome lines, not a single number.** `JobOutcomeLine {outcome, quantity, reason_code, note}`, several per job, with a hard constraint that the lines sum to the job's target quantity before the job can close. That constraint is what keeps yield analytics trustworthy — without it the denominator quietly rots.
- **Three outcomes, separated because their root causes are disjoint:**
  - **Good** — usable.
  - **Defect** — finished but unacceptable: pock marks/zits, stringing, under-extrusion, warping, visible layer lines, dimensional out-of-tolerance, support scarring. Points at material, profile, temperature, nozzle wear, or drying.
  - **Failed** — never finished: bed adhesion loss, spaghetti, nozzle clog, filament runout, layer shift, collision, thermal abort. Points at adhesion, mechanics, filament path, or power.

  Collapsing both into a single "scrap" count destroys exactly the signal that makes the number actionable. A plate of 8 might close as 5 good / 2 defect (pock marks) / 1 failed (detached).
- **Outcomes are captured at Mark ready, defaulted to all-good.** The operator is standing at the printer holding the parts at exactly the moment they clear the bed, so that's where the counts are entered — one tap accepts "all good," and the form only expands when something actually went wrong. Requiring deliberate entry on every job would be friction on the single most-repeated interaction in the product, and a farm that finds it tedious will stop recording within a week, taking the yield data with it.
- **Outcomes stay amendable after the job closes.** Not every farm QCs at the bed — defects surface during post-processing, packing, or a customer complaint. Editing a job's outcome lines later re-runs the shortfall calculation, which means **a completed run can reopen** and offer a requeue days after it first hit 100%. This is correct rather than surprising: the units genuinely weren't good. It does mean "complete" isn't terminal, which is why a **closed** state exists to eventually lock a run's history (see Open decisions).
- Reason codes are **seeded with defaults but editable** — every farm develops its own failure vocabulary within weeks, and a fixed enum will be wrong for someone almost immediately.
- Per-plate-position attribution (knowing *which* of 8 slots failed) is deliberately out of scope: a bed-region problem shows up as a pattern in the counts anyway, and position tracking only pays off once that's already suspected.
- **Shortfall loop.** Only good units satisfy a requirement, so defect and failed units automatically leave a run short — surfaced as a shortfall with a one-action requeue. Requeueing produces another whole plate and overshoots again, which is expected and harmless. This closed loop is the entire payoff of keeping demand and execution separate, and is precisely what a queue-only tool can't do.
- **Combined progress = discrete counts + a time-weighted bar.** Progress is weighted by each part's estimated print time (already derived in Phase 4), never by part count — 40 of 41 parts done is not 97% when the 41st is a 14-hour panel — and the currently-running job contributes its live percentage:

  `(completed_time + Σ running_jobs(job_time × live_percent)) ÷ total_required_time`

  The identical function serves a production run, a run line, and a part requirement; only the depth it's evaluated at changes.
- **Two numbers are always shown together:** a discrete count ("24 of 40 good"), which is auditable and trustworthy, and the blended bar, which is smooth and includes live job progress. Either one alone is jumpy or unverifiable.
- **Progress can move backwards** — a failed plate requeues and grows the total required time, so the bar drops. This is kept as-is because it's honest, but the drop is marked visually on the bar so it doesn't read as a bug.
- Nothing blended is persisted: discrete counters are stored, and the percentage is computed on read from live connector state. A value that depends on a live MQTT percentage is stale the moment a printer disconnects.
- Carried caveat: the printer's reported percentage is layer-based, not time-linear — a tall part's final 10% of layers can be 25% of its time. Fine for a progress bar, not quotable as an ETA without smoothing against elapsed time.
- **One production view, two lenses — the Queue page.** Default grouping is *by run*: expandable run → line → requirement → jobs, where an unnamed single-line run is a bare row with nothing to expand, so a solo operator sees a flat job list and nothing more. The alternate grouping is *by dispatch order* — the flat execution queue with the tree ignored, which is what answers "what prints next." Same data, same page, one toggle. The backfill tier renders as its own section below the queue rather than interleaved: it isn't competing for position, and showing it in the ordering would imply a priority relationship that doesn't exist. The printer-centric fleet view (Phase 1) stays separate — it answers "what is this machine doing," a third question that shouldn't try to be the queue.
- **Buildable units** were removed from Phase 6 (2026-10-16). If this phase wants a "complete sets" number per assembly line, define it here against Phase 8's real good-unit counts.
- Estimated versus **actual** print duration (captured per job in Phase 7) is reportable here, both as an accuracy check on Phase 4's estimates and as the input to printer utilization in Phase 18.
- Yield is sliceable by part, printer, material, filament profile, **file revision** (see Phase 7 — jobs record the revision they printed, which is what makes a defect-rate change traceable to a model tweak rather than a mystery), and time period. The data model lands here; the reporting surfaces are Phase 18 — Analytics dashboard, consistent with the plan's standing rule that data capture precedes the UI that needs it.

## Phase 12 — Intelligent queue matching

- Suggests which printer to assign a queued job to based on currently loaded filament (material + color match), to minimize spool swaps.
- Operator confirms suggestions rather than the system auto-claiming a machine.
- Only printers in the idle state (not awaiting clear) are considered candidates.
- When several suggested assignments dispatch at once, printer starts are staggered by a configurable delay rather than firing simultaneously, to avoid tripping a shared circuit. Printers can optionally be tagged into circuit groups (reusing the existing tag system) so staggering only applies within a shared circuit, not farm-wide.
- Later: factor in printer capability (from machine profiles, Phase 2 — Profiles — nozzle size, bed volume, enclosure) so impossible assignments are never suggested.
- Later: optimize across the whole queue at once, not just job by job.

## Out of scope for now

- Native mobile app (the webapp will be responsive-first).
- Multi-tenant / hosted SaaS (organizations, team invites, billing). OpenFarm is single-tenant and self-hosted. The old Phase 19 was removed for this reason; later phase numbers are not renumbered.
- **Inventory / stock management of printed parts.** OpenFarm's job is to *produce*, not to hold a ledger of what's on the shelf. No stock-on-hand balance, no consuming existing stock to reduce a run's demand, no tracking of over-produced units. A requirement of 5 filled by a plate of 8 is simply complete.
- **Cross-run pooling of identical parts.** Two run lines needing the same part print separately (see Phase 7). This follows directly from having no stock ledger — pooling without one just moves the bookkeeping problem rather than solving it.
- **Per-unit serialization.** Produced units are counted, not individually identified. No serial numbers, no per-unit history.
- **Post-print fulfillment state** (assembled / boxed / shipped). Everything after a part comes off the bed is fulfillment, not print-farm operation; Phase 16 — Order integration is its natural home if it's ever wanted.

## Open decisions

- License model for eventual public release (permissive vs. source-available/open-core) — worth deciding before the first public commit.
- Bambu Lab's LAN-only + Developer Mode requirement disables that printer's connection to Bambu Cloud/Handy while active — decide how clearly to surface this trade-off to users before they connect a printer. This is a real, immediate trade-off for Phase 1's own development, not just a future user-facing concern.
- Sourcing default printer/filament profile data is resolved by design: Phase 2 is import-your-own-bundle only, so OpenFarm never bundles or needs to license third-party slicer profile data as defaults.
- Retention/aggregation strategy for the printer status-history log (Phase 1) once it's been running for a while — raw timestamped events are fine to start, but worth revisiting before the table grows large, and before Phase 18 — Analytics dashboard leans on it heavily.
- HMS hardware-fault/alert surfacing (Phase 1) — the printer's live connection already reports an active fault list (severity + subsystem) and a fatal print-error code, but Phase 1 deliberately doesn't model or display either; decide which later phase owns surfacing it (Phase 9 — Maintenance tracking and Phase 17 — Notifications are the two natural homes) rather than letting it stay silently unaddressed.
- Key management for connection-secret encryption: an install-generated key is enough for self-hosted; moving to a secrets-manager/KMS-backed key is an optional hardening step, not urgent for MVP.
- Whether automated bed-ejection setups (conveyor belts, auto-eject firmware) should ever let a printer skip `AwaitingClear` and self-idle. Nothing in the plan models them today, and the state exists specifically to stop a dispatch onto an uncleared bed — but a per-printer "self-clearing" flag is the obvious shape if it's ever wanted.
- Local connector agent's transport, machine-credential format, and pairing/rotation flow (how a customer installs and authorizes an agent for their farm) aren't decided — not needed for MVP, but the printer connector should still be built as a swappable boundary in Phase 1 — Fleet management + live Bambu integration so this doesn't force a rewrite later.
- Bambu's local MQTT/Developer Mode access is unofficial-but-permitted, not a versioned/guaranteed API — firmware updates have previously narrowed third-party access. Worth an explicit maintenance-risk note for `BambuLanConnector`, not a one-time build-it-and-forget item.
- Whether non-printed BOM components (Phase 6) earn their place at all while they gate nothing and track no stock — they buy BOM truthfulness and non-filament cost input for Phase 18, at the price of a polymorphic BOM line. Cheap to keep now, expensive to add later; cuttable if the cost input turns out not to matter.
- Whether `units_per_print` (Phase 7) should ever be *derived* rather than operator-set for files that require slicing — an in-app slice knows exactly how many objects it placed, but Phase 4's slice is estimate-only and doesn't persist its output. Defaulting to 1 with an operator override is the MVP answer.
- Whether an unlimited-quantity run line should surface any progress indicator at all beyond cumulative counts, or whether the absence of a completion percentage is itself the correct UI.
- How a production run reaches the terminal **closed** state (Phase 7/8): explicitly by the operator, automatically after a configurable idle period past completion, or both. Until it's closed, late-logged defects can reopen a finished run, which is the intended behavior — but a run that can reopen indefinitely makes historical reporting unstable, so the window matters and is likely farm-specific.
- Default values for the backfill tier's two safety limits (Phase 7): how many printers one unlimited line may occupy at once, and whether a cumulative-unit ceiling should be on by default or opt-in. Both are guesses until a real farm runs the queue dry a few times.
- Retention/aggregation for job outcome lines (Phase 8) once yield history accumulates — same shape of question as the printer status-history log above, and worth answering at the same time.
