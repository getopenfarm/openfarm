# Feature Specification: Phase 4 — Part Library (with Sliced Files & In-App Slicing)

**Feature Branch**: `[007-part-library]`

**Created**: 2026-07-19

**Status**: Draft

**Input**: User description: "Phase 4"

## Clarifications

### Session 2026-07-19

- Q: How should a part declare its filament requirement, given PETG-sliced files should match any PETG spool by default unless narrowed to a specific brand/color? → A: Generic type + optional override — store the generic material type (e.g. "PETG") parsed directly from the `filament_type` metadata as the baseline match; operator may optionally attach a specific Filament Profile/color-variant to narrow matching to an exact brand/color.
- Q: How should a part declare which printers it's physically compatible with, given it should be printer-agnostic but nozzle-size-aware? → **Revised below** — filament-diameter matching is dropped entirely; see the later clarification on nozzle-diameter auto-detection.
- Q: Given estimated print time and filament usage are reliably embedded in already-sliced file metadata, how should the system use the parsed values? → A: Auto-parse, authoritative — parse and store the value directly with no operator review step.
- Q: Should this phase flag a part's file as potentially stale in some way? → A: No — deferred out of this phase entirely (per direct instruction, not a formal question). There's no staleness concept to build; replacing a part's file is a direct, immediate replacement, not a flag-and-decide-later workflow.
- Q: Phase 23 (In-app slicing) is being merged into this phase, since a raw/unsliced file has no parseable time/weight/nozzle metadata until something actually slices it — should manually uploading an already-sliced file remain supported alongside automatic in-app slicing? → A: Both paths supported — an operator can upload a file requiring slicing (system automatically invokes a headless slicer CLI) or upload an already-sliced file directly.
- Q: Which headless slicer engine should in-app slicing invoke — OrcaSlicer, Bambu Studio, or both? → A: Configurable default with per-part override — an organization-level Settings option sets the default engine (OrcaSlicer recommended: open-source, broadest printer support, already the Phase 2 import source), and each part's in-app-slicing request pre-fills that default but lets the operator pick a different engine for that specific request.
- Q: When does in-app slicing actually run — on an operator-invoked "pick a machine profile, slice now" request, or automatically at specific trigger points? → A: Automatically, whenever a part's file requires slicing (initial upload or a replacement upload) and the part has a material available. This phase builds only this automatic-at-upload trigger and the reusable in-app-slicing capability itself; a separate future on-demand trigger at job-dispatch time (Phase 7, once a Job entity exists) is a forward-compatibility note, not built here.
- Q: Is uploading a new file for a part additive or a direct/destructive replacement, and what happens to a job already in the queue (Phase 7) either way? → A: A part holds exactly one file, so every upload after the first is necessarily a replacement, never additive. A queued/printing job is unaffected either way: Phase 7's job design (`docs/FEATURE_PLAN.md`) locks a job onto a copy/reference of the print-ready content it needs at queue time, not onto "whatever the part's file currently is."
- Q: Should a Part hold a flat collection of multiple Files, or exactly one? → A: **Exactly one, always.** Given Assembly (Phase 6) already exists to combine multiple parts, a Part itself stays atomic — strictly one file per part, period. A 3MF that happens to bundle multiple plates/objects is still treated as one indivisible file belonging to one Part — the system does not split it into multiple Parts, nor warn about multi-plate content as such. *(A later clarification below partially reopens what "does not detect" means here: per-plate **filament-requirement** detection is now in scope, though splitting into multiple Parts/thumbnails-per-plate is not.)*
- Q: Should the system persist an actual sliced-output file when it auto-slices an STL/3MF, or only the derived estimate/matching data? → A: **Only the derived data — never a persisted sliced-output file, unless the upload itself already was one (G-code).** Automatic in-app slicing of an STL/3MF is purely to derive nozzle diameter, generic material type, estimated print time, and estimated filament weight, which are stored directly on the Part; the slicer's actual output is discarded.
- Q: Should a part ever exist with a Machine Profile explicitly linked to its file? → A: **No — dropped entirely.** A part's compatibility is expressed purely through its derived nozzle diameter; there is no concept of linking a part to a specific Machine Profile record. (An optional narrower link to a specific Filament Profile/color-variant, for exact brand/color matching, is unaffected and still allowed.)
- Q: Should an unparseable already-sliced file, or a file requiring slicing with no material available, ever be saved with manual-fallback estimates — or must every part have real, derived data before it can be saved at all? → A: **No manual fallback of any kind — a file must be fully parseable/sliceable before the part it belongs to can be saved.** If an already-sliced file's nozzle diameter, material type, or time/weight can't be parsed, the add/replace is rejected outright. If a file requires slicing and no material is available, the add/replace is also rejected — it is never saved in a pending or partial state. There is no manual numeric entry for nozzle diameter, print time, or filament weight anywhere in this phase.
- Q: Given every saved part now always has complete, derived data, is a separate "job-ready" / "not yet job-ready" concept still needed? → A: **No — dropped entirely.** Every part that exists is, by construction, fully valid and usable — there's nothing to flag as "not ready." The only remaining distinction a part carries is whether its file **requires slicing** (meaning Phase 7 will need to slice it again for real toolpath data at job-dispatch time, since no sliceable output is persisted) or was **already sliced** on upload (meaning its stored file can be sent to a printer directly).
- Q: Should a part's thumbnail still be manually uploaded, or derived automatically from its file? → A: **Derived automatically, not manually uploaded.** For a file requiring slicing, the thumbnail is rendered from the model as part of the in-app slicing pass. For an already-sliced file (G-code, or a 3MF that already contains one), the thumbnail is extracted from its embedded preview image — G-code embedding a base64 preview image in comments, and Bambu-style `.gcode.3mf` embedding one in its metadata, are both standard, widely-supported slicer/firmware conventions (used for on-device screen previews), so this is reliably available for already-sliced files too. For a 3MF bundling multiple plates, only the first plate's image is used. Deriving a thumbnail is best-effort — failure to produce one does not block saving the part, unlike its nozzle-diameter/material/estimate data, which must succeed.
- Q: Should there be an organization-configured default material that automatic slicing falls back to when a part doesn't specify one? → A: **No — dropped entirely.** There is no organization default material. An intended Filament Profile is REQUIRED from the operator whenever a part's file requires slicing (no fallback exists); everything else follows the same two-tier pattern already established for filament matching — the operator either selects a Filament (matching any color/brand variant of that generic material, e.g. "Any PETG") or a specific filament variant (an exact brand/color), never a third "leave it unspecified" option for a file that needs slicing.
- Q: Should there be an organization-configured default nozzle diameter (and filament diameter) that automatic slicing targets? → A: **No — dropped entirely, and filament-diameter matching is dropped from this phase altogether** (it's a virtually-uniform 1.75mm across the modern desktop-printer market this project targets, and printer telemetry doesn't expose it anyway — not worth the catalog work to track). The only remaining organization-level Slicing Default is the default slicer **engine**. Nozzle diameter is instead **auto-detected from the farm's currently-registered printers**: automatic slicing targets whichever nozzle diameter is most common among them, with no operator input and no configurable setting involved. If the printer catalog has no registered printer with a known nozzle diameter yet, automatic slicing cannot proceed and the add/replace of a part whose file requires slicing is rejected until at least one exists. (Real job/printer matching at dispatch time — Phase 7 — will separately depend on which printers and feed-slot materials are actually available then; this auto-detected value is only Phase 4's own slicing-target heuristic, not that matching logic.)
- Q: Where does a printer's nozzle diameter actually come from, given Phase 1's `Printer` entity doesn't store it and this phase can't invent a new standalone data point? → A: **This phase finally wires the Printer ↔ Machine Profile link that `docs/FEATURE_PLAN.md`'s own Phase 1 dependency notes already earmarked for it** ("that linkage... stays deferred, until whichever later phase actually consumes it (Phase 4 — Part library)"). A printer's nozzle diameter is read from its linked Machine Profile (Phase 2, which already models `nozzle size`) — no duplicate field is added to `Printer` itself. The link is optional at printer-creation time (a matching Machine Profile may not have been imported yet), so a printer can exist without one; **only a printer with a Machine Profile linked counts as a "real fleet member" for nozzle-diameter auto-detection** — an unlinked printer simply doesn't contribute to the "most common nozzle diameter" calculation (FR-005a) or to FR-006's "at least one known nozzle diameter" check.
- Q: Should adding/replacing a part whose file requires slicing auto-save the moment the background slice succeeds, or should the operator review what was derived first? → A: **Review, then confirm** — the operator sees the derived nozzle diameter, material type, print-time/weight estimate, and thumbnail, may attach or change the optional narrower Filament Profile/color-variant override at that point (having now seen what was actually derived), and must explicitly confirm before the Part is created or its file is replaced. Discarding a reviewed result instead of confirming it is also supported — nothing is saved, exactly as if processing had never run. **This narrows, not reverses, the earlier "auto-parse, authoritative, no operator review step" answer**: that answer is still exactly true for the *numbers themselves* — there is still no manual entry or numeric override of nozzle diameter, material type, print time, or filament weight anywhere in this phase, at review time or ever. The only thing newly gated on operator action is *whether a successfully-derived result gets committed at all*, mirroring the Preview → Confirm shape Phase 2's slicer-bundle import already established (`specs/003-slicer-profile-import/`) for the same reason: a result the system itself produced (whether by parsing or by slicing — see the next clarification) is worth a look before it becomes permanent catalog data, even though nothing about the result itself is hand-edited. *(Superseded/broadened by the next clarification — initially scoped to the requires-slicing path only, now uniform across every file type.)*
- Q: Can a Part require more than one filament, to represent a real multi-color/AMS part sliced or pre-sliced with several distinct materials across different color slots? → A: **Yes — a Part holds a collection of filament requirements, not a single one.** Each requirement carries its own generic material type (e.g. "PETG") and its own optional narrower Filament Profile/color-variant override; an already-sliced file's own embedded multi-color mapping (e.g. a Bambu AMS slot assignment) is parsed into one requirement per detected slot, each independently narrowable. A file requiring slicing still targets exactly one operator-specified Filament per in-app slice (building true multi-material *slicing itself*, where different physical regions of one model get different materials, is out of scope for this phase) — an in-app slice therefore always produces exactly one filament requirement, though the operator may still attach its narrower override at the review/confirm step above. This supersedes the earlier single-`Filament`-per-Part framing throughout FR-002/FR-012/FR-012a and the Key Entities section.
- Q: Given a 3MF's already-sliced/requires-slicing status already has to be *classified* before it's known which processing path applies, and a G-code/already-sliced file's metadata still has to be *parsed* even though nothing external is invoked for it, should the review/confirm step really only apply to the requires-slicing path, or should every add/replace go through the identical Processing → Ready for Review → Confirm/Discard shape regardless of file type? → A: **Every add/replace goes through the same uniform pipeline, regardless of file format.** There is no longer a synchronous, direct-save branch for an already-sliced file: a G-code (or already-sliced 3MF) upload still reaches "processing" and then "ready for review" exactly like an STL/unsliced-3MF upload does — it simply resolves near-instantly in practice, since parsing embedded metadata takes no external process the way slicing does. The operator experience is identical in every case: submit, wait briefly for a result, review the derived nozzle diameter/material(s)/estimates/thumbnail (attaching narrower filament overrides at that point, for any file type, not only a slicer-derived one), then confirm or discard. **Why unify rather than keep the two-shape design**: the two paths already had to share almost everything (the same derived-data shape, the same rejection rules, the same thumbnail/estimate requirements, the same review/confirm mechanics for a multi-color already-sliced file) — the only real difference was *how* the result gets produced (an external slicer process vs. reading embedded metadata), which is exactly the kind of difference that belongs behind one interface's implementation, not exposed as two different API/UI shapes. This also removes the one place operators would otherwise need to learn two different interaction patterns for what is, from their point of view, the same action ("add a part from a file").
- Q: Does the operator have to finish filling out the whole add-part form (name, tags) before file processing can even begin, or can those details be entered while processing runs in the background? → A: **Attaching the file (plus a Filament pick, if the file needs slicing) starts processing immediately — name and tags are entered/finalized concurrently, while processing runs, and are only actually needed at the confirm/save step.** The add-part experience is one continuous form/dialog, not two separate round trips the operator has to consciously sequence: the moment a file (and, if required, a Filament) is attached, the system begins processing it in the background; the operator can keep typing the part's name, add tags, etc. in the same dialog while that runs. The Save action is disabled until processing reaches "ready for review" (and, for a new part, until a name has been entered) — once both are true, Save becomes enabled, submitting the name/tags/any narrower filament overrides together as the confirm step; Cancel at any point is the same as discarding. Replacing an existing part's file follows the identical shape, minus name/tags (unaffected by a replace).
- Q: What happens when an operator adds a part whose file requires slicing (STL, or an unsliced 3MF) without specifying a Filament — is this always rejected (FR-002/FR-006 as originally written, which listed "no Filament specified" as a rejection case), or should the system support a real "any material" option, deferring the actual material commitment to whenever the part is later matched to a machine/job? → A: **Yes — Filament becomes optional for a requires-slicing file too, defaulting to a genuine "any material" wildcard, not a rejection.** This phase still must run its own immediate in-app slice right now, to satisfy the standing "a part is never saved incomplete" rule — a slicer CLI cannot run without *some* concrete material's settings as input — so when no Filament is specified, the system slices against a **fixed, internal, non-operator-configurable generic default material** (not an organization Setting — an org still cannot configure this) purely to produce the immediate estimate/nozzle-diameter/thumbnail data, and stores the resulting filament requirement as **fully unconstrained** (no material type recorded at all — broader than "any PETG," which still requires PETG specifically). **This is a real, accepted accuracy tradeoff**: the estimate is a best-effort approximation against a placeholder material, not a guarantee of the part's actual eventual print time/weight once matched to whatever material a real job uses (Phase 7) — the part is still always *complete* (nozzle diameter/estimate/thumbnail are always present, per FR-006), just not necessarily *accurate* for whatever material it's ultimately printed in, narrowing SC-003's "100% accurate" framing specifically for this wildcard case. The operator can still override at any point — either by specifying a real Filament at submit time instead of leaving it blank (unaffected, works exactly as before), or by narrowing the resulting unconstrained requirement to a specific Filament Profile/color-variant at the confirm step (FR-012a), exactly like any other requirement. **This does not apply to an already-sliced file** — its process parameters (nozzle/bed temp, retraction, flow) are physically baked into the toolpath for one specific material once sliced, so an already-sliced file's requirement can never be widened to "any material"; only a requires-slicing file, which gets a genuinely fresh slice whenever its real material is eventually known, can honestly support this.
- Q: Does a real sliced file (G-code / `.gcode.3mf`) actually carry per-slot/per-plate color information the system could parse, and — given a 3MF bundling multiple plates was previously ruled out of scope for anything beyond its thumbnail — should a multi-plate 3MF where different plates use different materials/colors (e.g. plate 1 black PETG, plate 2 white PLA) now be parsed into separate filament requirements too? → A: **Yes to both — this partially reopens the earlier multi-plate limitation, specifically for filament-requirement detection.** A sliced file's own metadata reliably carries per-slot material *and* color (standard Bambu/OrcaSlicer G-code header convention, e.g. `filament_type`/`filament_colour`), and — for a genuinely multi-plate `.gcode.3mf` — each plate's own embedded G-code/metadata carries this same information independently. The system now scans **every** plate and **every** AMS slot within each plate for its detected material + color, **groups the results by distinct (material type, color) pairs** (not one row per slot/plate), and produces one filament requirement per distinct pair. A 4-plate file where all four plates are black PETG collapses to **one** filament requirement; a 4-plate file with plate 1 black PETG, plate 2 white PLA, plate 3 black PETG (a repeat of plate 1's combination), plate 4 red PETG produces **three** — the repeated combination on plate 3 does not create a fourth, duplicate row. Narrowing one of these grouped requirements to a specific Filament Profile/color-variant applies uniformly to **every** plate/slot sharing that requirement's (material, color) pair, not to one plate individually — there is no per-plate or per-slot narrowing independent of this grouping. **What stays exactly as before**: the thumbnail is still derived from the first plate only (FR-014, unaffected); the system still never splits a multi-plate 3MF into multiple Parts, still never warns about multi-plate content as such, and a Part's estimated print time/weight still represent the whole file as one number each — now computed as the **sum across every plate**, since a multi-plate G-code executes all of its plates as one continuous physical print. Detected color is informational/grouping data only — it is never itself a matching criterion; matching still runs purely on generic material type (and, if the operator narrows, the exact Filament Profile/color-variant), exactly as already specified.
- Q: Should an operator be able to pick a target Filament/color before the file has even been processed, given that lets them choose a color the system hasn't actually confirmed the file supports yet? → A: **No — `filamentId` is removed from the Add/Replace request entirely.** The operator never selects a material at upload time for any file type. Instead, the system resolves the automatic in-app slicing target purely from the file's own content: an unsliced 3MF's project-level filament assignment (Orca Slicer/Bambu Studio require picking one before a project can be saved, so this is reliably present) is parsed and used directly, with no operator input; an STL, which structurally cannot carry any material data, falls back to a fixed internal generic default (the existing FR-002a mechanism, now the *only* case it applies to). The operator's sole material-related action anywhere in this flow is narrowing an already-derived filament requirement to a specific Filament Profile/color-variant at the review/confirm step (FR-012a) — after the real result is known, never before or during processing.
- Q: Given `filamentId` no longer exists on the request, does "any material" (FR-002a's fully unconstrained requirement) still apply to every file requiring slicing, or does it narrow further? → A: **"Any material" now applies to STL only.** A 3MF, sliced or unsliced, is expected to always carry real filament metadata — Orca Slicer/Bambu Studio require a material selection to save any project, sliced or not — so an unsliced 3MF whose project-level material assignment cannot be parsed is treated as a genuine parsing failure and rejected outright (FR-006), exactly like an already-sliced file's unparseable metadata, **not** as a fallback to "any material." Only an STL, which can never carry material data by construction, legitimately produces a fully unconstrained requirement — that case is not a failure, it's the expected outcome for that format.
- Q: Should a multi-plate file's thumbnail stay limited to its first plate now that filament-requirement detection already scans every plate, or should every plate get its own visible thumbnail? → A: **Every plate gets its own thumbnail, for both already-sliced and requires-slicing multi-plate files.** For an already-sliced multi-plate 3MF, each plate's own embedded preview image is extracted (the same convention already relied on for the first plate). For a multi-plate file that still requires slicing, the in-app slicing pass renders one thumbnail per plate rather than one for the whole file. The Part's single catalog-list thumbnail remains the first plate's image (unchanged); the full per-plate set becomes visible in the part's own review/detail view. The file itself is still never split into multiple Parts — this only changes what's shown, not the Part's atomicity.
- Q: Must an operator wait for a part's estimated print time/weight (and thumbnail) to finish resolving before they're allowed to save it, given a large file's in-app slicing can take real time and an operator tuning their own slicer already knows these numbers independently? → A: **No — saving no longer waits on the estimate.** Nozzle diameter and material are now resolved before slicing itself even runs (FR-002/FR-002a make them inputs to the slice, not outputs of it), so the system reaches a "ready to save" point almost immediately regardless of file size — well before a large file's actual slice/render finishes. An operator may confirm/save at that point (once a name is entered, for a new part); print time, filament weight, and the thumbnail continue resolving in the background and populate onto the already-saved part once ready, pushed to the operator's view the same way every other live update in this feature already is. An operator who instead keeps the review dialog open sees the same numbers arrive before confirming, exactly as before — this only removes the requirement to wait, it doesn't remove the ability to. If the deferred slice ultimately fails, the part remains saved with its estimate shown as unavailable rather than being rolled back or flagged as needing reprocessing — this is now the one case in this phase where a part can carry a permanent gap in its derived data. Nozzle diameter and material remain always-required and still block saving if they can't be resolved (FR-006) — this exception applies to print time/weight/thumbnail only.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Add and browse parts in the catalog (Priority: P1)

As a print farm operator, I want to add a part to a reusable catalog with just one file, so I have a single place to browse and manage everything I print — with per-plate thumbnails and real compatibility data derived automatically from the file itself, never entered by hand, configured up front, or chosen by me before the system has actually looked at the file.

**Why this priority**: This is the foundational catalog capability every other story in this phase builds on — a file replacement or tag all attach to a part that must exist first. It's independently valuable on its own: an operator gets a real, browsable product catalog with genuine data on every part, never a placeholder.

**Independent Test**: Can be fully tested by attaching one file (STL, 3MF, or G-code) that the system can successfully process — no material selection required from the operator at any point — confirming processing begins immediately while the name/tags remain freely editable, confirming Save stays enabled as soon as nozzle diameter/material resolve and a name is entered (without waiting for the estimate/thumbnail to finish), then reviewing and confirming the resulting derived data, and confirming the part appears in the catalog with per-plate thumbnails and real nozzle-diameter/material data — via the identical attach → concurrently edit → review → confirm sequence regardless of which file type was uploaded.

**Acceptance Scenarios**:

1. **Given** no parts exist yet, **When** an operator adds a new part by attaching an STL, **Then** the system immediately begins automatically slicing it — against a fixed internal generic default material, since an STL never carries material data of its own — targeting the farm's most common nozzle diameter, while the operator can still enter/edit the part's name and tags in the same dialog; once nozzle diameter/material resolve the operator may confirm (once a name has been entered), saving the part with a fully-unconstrained "any material" filament requirement even before its estimate/thumbnail finish resolving.
2. **Given** no parts exist yet, **When** an operator instead adds a new part by attaching an unsliced 3MF, **Then** the system parses the project's own filament assignment, automatically slices against it and the farm's most common nozzle diameter, and — exactly like the STL path — lets the operator confirm as soon as nozzle diameter/material resolve, with the resulting filament requirement carrying the parsed generic material type (e.g. "Any PETG"), not fully unconstrained.
3. **Given** no parts exist yet, **When** an operator instead adds a new part by attaching one already-sliced file (G-code, or a 3MF that already contains sliced G-code), **Then** the system parses it and presents the parsed result for review before anything is saved, with the name/tags fields available to fill in throughout; confirming (once a name has been entered) stores the file as-is along with its per-plate extracted thumbnails and parsed nozzle diameter/material/estimates, which are typically all available together since parsing needs no external process.
4. **Given** the farm has no registered printer with a Machine Profile linked yet, **When** an operator tries to add a part whose file requires slicing, **Then** the add is rejected — automatic slicing has no nozzle diameter to target.
5. **Given** an operator is adding a part, **When** its file cannot be successfully parsed or sliced for any reason (including an unsliced 3MF with no parseable project-level material), **Then** the add is rejected outright — no part is saved with an unresolved nozzle diameter or material, and no review step is ever reached.

### User Story 2 - Automatically derive a part's data via in-app slicing (Priority: P1)

As a print farm operator, I want the system to automatically slice my part's file when it needs slicing (STL, or a 3MF that isn't already sliced) — resolving its own target material from the file itself and targeting whichever nozzle diameter is most common across my fleet — so I get real nozzle-diameter/material data and per-plate thumbnails without manually pre-slicing it myself, picking a material up front, configuring anything, or the system needing to keep a separate sliced-output file around.

**Why this priority**: This is the headline capability this phase folds in (merging the former Phase 23 — In-app slicing) specifically so every part in the catalog carries real, usable data — without it, adding a part from a raw model would need a manual round-trip through an external slicer first. It's ranked alongside Story 1 because together they're this phase's minimum demoable capability: add a file, get a fully-described part.

**Independent Test**: Given a part is being added with a file requiring slicing, and the farm has at least one registered printer with a Machine Profile linked, can be tested by confirming the system resolves a target material from the file itself (or the fixed internal default, for an STL) with no operator input, automatically invokes the configured slicer engine against that material and the farm's most common linked nozzle diameter, that nozzle diameter/material land in a reviewable state early enough for the operator to confirm before the render/estimate finishes, that a fully successful slice additionally shows per-plate rendered thumbnails and parsed estimated print time/weight, and that the part only actually appears in the catalog once the operator confirms it — with no separate sliced-output file ever created, and confirming that a slicing failure occurring before confirmation rejects the operation entirely rather than saving anything with an unresolved nozzle diameter/material.

**Acceptance Scenarios**:

1. **Given** an organization has not yet configured a default slicer engine, **When** a part's file requires slicing, **Then** the system uses a sensible built-in default engine (OrcaSlicer) for automatic slicing.
2. **Given** the farm has printers with a Machine Profile linked, **When** a part's file requires slicing, **Then** the system automatically invokes the configured engine to slice it against the material resolved from the file itself (FR-002/FR-002a) and the farm's most common linked nozzle diameter, presents the resulting nozzle diameter/generic material type for review as soon as they resolve (ahead of the estimate/thumbnail, per Story 1), and once the slice fully completes also presents estimated print time/weight and a rendered thumbnail per plate — the slicer's toolpath output itself is discarded, and the part's file remains exactly as uploaded.
3. **Given** the farm's printers-with-a-linked-Machine-Profile are split across two different nozzle diameters, **When** automatic slicing runs, **Then** it targets whichever nozzle diameter the most of those printers currently have, without asking the operator to choose; a printer with no Machine Profile linked is simply not counted.
4. **Given** an operator wants a specific part sliced with a different engine than the organization default, **When** they choose an override engine for that part, **Then** only that part's automatic slice uses the override, without changing the organization-wide default.
5. **Given** the configured slicer engine fails or times out slicing a part's file (e.g. non-manifold geometry) **before** the operator has confirmed, **When** that happens, **Then** the add or replace operation is rejected entirely — the failure is surfaced clearly, and no part (or, for a replacement, no changed data) is saved. **Given** the same failure instead occurs **after** the operator already confirmed an early save (nozzle diameter/material resolved, estimate/thumbnail still pending), **When** that happens, **Then** the part remains saved and the failure only marks its estimate/thumbnail as unavailable.
6. **Given** automatic slicing is in progress for an add or replace request, **When** an operator checks on it, **Then** the system shows a clear in-progress state; once nozzle diameter/material resolve, the state allows confirming even if estimate/thumbnail are still resolving — nothing is visible in the catalog until the operator actually confirms.
7. **Given** nozzle diameter/material have resolved (whether or not the estimate/thumbnail have too), **When** the operator reviews the available derived data, **Then** they may optionally attach or change a narrower Filament Profile/color-variant override for the resulting single filament requirement and then confirm, which creates the part (or applies the replacement) immediately from whatever has already been derived; **or** they may discard the reviewed result instead, in which case nothing is saved and the part (or its prior file/data, for a replace) is exactly as if the slice had never run.

### User Story 3 - Manually provide an already-sliced file (Priority: P1)

As a print farm operator, I want to directly provide an already-sliced file for a part — one I sliced myself externally, or one downloaded pre-sliced with no original model available — so I'm not limited to whatever in-app slicing produces, and the file itself is retained since I already have the real sliced output in hand.

**Why this priority**: Keeps the catalog useful for operators with existing tuned external slicer profiles or pre-sliced files with no original model behind them. Ranked alongside Stories 1–2 since, together, they're what makes every part in the catalog fully described.

**Independent Test**: Can be fully tested by adding or replacing a part's file with an already-sliced file, confirming the system parses its nozzle diameter, generic material type(s), and estimates directly from it and extracts a thumbnail per plate, presents that result for review exactly like a requires-slicing add/replace would (with all fields available together, since parsing needs no external process), and — once confirmed — stores the file as-is; rejecting the operation instead (with no review step ever reached) if any of that can't be parsed.

**Acceptance Scenarios**:

1. **Given** an operator uploads an already-sliced file (G-code, 3MF, or brand-specific bundle) for a new or existing part, **When** its nozzle diameter, material type, and estimates can all be parsed successfully, **Then** the parsed result is presented for review the same way a slicer-derived result would be, and once confirmed the file is stored as-is (unlike an automatic slice, nothing is discarded here) with that parsed data and a thumbnail extracted per plate.
2. **Given** an already-sliced file was sliced for PETG with a single material, **When** it becomes the part's file with no further narrowing, **Then** the system parses one filament requirement carrying "PETG" as its generic material type, matching any PETG spool/filament by default.
3. **Given** an already-sliced file uses AMS-style multi-color mapping across several slots, or is a multi-plate file where different plates use different materials/colors, **When** an operator adds it, **Then** the system scans every plate and slot, groups the results by distinct (material type, color) pairs, and parses one filament requirement per distinct pair — a 4-plate file that's all black PETG produces one requirement; one with plate 1 black PETG, plate 2 white PLA, plate 3 black PETG (repeating plate 1's pair), and plate 4 red PETG produces three, not four. The operator can independently link the specific filament profile/color-variant each requirement corresponds to, narrowing that requirement's match (applying to every plate/slot sharing its material+color pair) without affecting the others.
4. **Given** an already-sliced file in a format or state the system cannot fully parse (missing nozzle diameter, material type, or estimate), **When** an operator tries to add or replace with it, **Then** the operation is rejected — there is no manual-entry fallback for any of these values.
5. **Given** a part needs to run on a different nozzle-diameter target than its current file targets, **When** an operator wants both available at once, **Then** they create a separate Part record for the other target — replacing the existing part's file would discard the current one rather than keep both.

### User Story 4 - Replace a part's file (Priority: P2)

As a print farm operator, I want to upload a new file for an existing part, so I can fix or improve its design, or swap in a different result, without recreating the part or losing its name, tags, and other details — and without ever leaving the part in a broken state if the new file doesn't work out.

**Why this priority**: A real maintenance need once a catalog is in active use, but only matters after parts already exist (Story 1), so it's ranked after the core catalog stories. There's no staleness-tracking or multi-file complexity here — replacing is the whole operation, and it either fully succeeds or changes nothing.

**Independent Test**: Can be tested by uploading a replacement file for a part that already has tags and other details set, confirming the part keeps its identity and tags while its file, thumbnail, and derived data update to reflect the new one — and separately, by attempting a replacement with a file that fails to process, confirming the part's original file and data are completely unchanged.

**Acceptance Scenarios**:

1. **Given** a part with an existing file, **When** an operator uploads a replacement file (of either kind) that processes successfully and the operator confirms the reviewed result, **Then** the part's file, thumbnails, and derived data are all replaced while its name and tags remain unchanged; for a file requiring slicing, the operator may confirm as soon as the new nozzle diameter/material resolve, with the new estimate/thumbnails populating afterward exactly as for an add (FR-009c/FR-009d).
2. **Given** a part with an existing file, **When** an operator uploads a replacement file that fails to parse, or fails to slice **before** the operator confirms, **Then** the replacement is rejected, and the part's original file, thumbnails, and derived data remain exactly as they were — the same outcome as if the operator had discarded a reviewed-but-unwanted result instead. **Given** the replacement instead fails to slice **after** the operator already confirmed an early save, **When** that happens, **Then** the part keeps its new file/nozzle-diameter/material, but its estimate/thumbnails are marked unavailable rather than reverting to the prior file's data.

### User Story 5 - Organize the catalog with tags (Priority: P3)

As a print farm operator with a growing catalog, I want to tag parts by category or product line, so I can filter down to the parts I care about instead of scrolling a flat list.

**Why this priority**: Pure organizational convenience — valuable as the catalog grows, but the catalog is fully usable without it, so it's ranked last.

**Independent Test**: Can be tested by tagging several parts with different tag values and confirming the catalog can be filtered down to just the parts sharing a given tag.

**Acceptance Scenarios**:

1. **Given** parts exist with no tags, **When** an operator adds one or more tags to a part, **Then** those tags appear on the part and are available for filtering.
2. **Given** parts tagged with different values, **When** an operator filters the catalog by a tag, **Then** only parts carrying that tag are shown.

### Edge Cases

- What happens when an operator uploads a file that isn't STL, 3MF, or G-code at all? The system should reject the upload and state that only those formats are accepted.
- What happens when an uploaded 3MF's sliced/unsliced status can't be reliably determined from its own metadata? The system should treat it as requiring slicing (the safer default) and attempt automatic in-app slicing; if that also fails, the add/replace is rejected (FR-006).
- What happens when an uploaded 3MF bundles multiple plates/objects internally? The system treats the whole file as one indivisible file belonging to one part (never split into multiple Parts). It scans every plate (and every AMS slot within each) for filament requirements, grouping by distinct material+color pairs (see the dedicated clarification above) — estimated print time/weight are the sum across all plates — and now also derives a thumbnail **per plate**, not only the first (the first plate's image remains the one used in catalog/list views). What's still not attempted: splitting the file into multiple Parts, or otherwise warning about multi-plate structure beyond the filament-requirement/thumbnail detection itself.
- What happens when an operator adds an already-sliced file whose metadata has no parseable nozzle diameter, material type, or estimate? The add or replace is rejected — there is no manual-entry fallback for any of these values.
- What happens when an unsliced 3MF's own project-level filament assignment has no parseable material type? The add or replace is rejected, exactly like an already-sliced file's unparseable metadata — this is a genuine parsing failure, not a case that falls back to "any material" (that fallback exists only for an STL, which structurally never has a material to fail to parse).
- What happens when the configured slicer engine's CLI process crashes, times out, or fails on unsupported/non-manifold geometry during automatic in-app slicing? If this occurs **before** the operator has confirmed, the add or replace is rejected entirely, with the failure surfaced clearly (not silently swallowed), and — for a replace — the part's existing file and data left completely unchanged. If it occurs **after** an early confirmation (FR-009c/FR-009d), the already-saved part is left in place — only its estimated print time/weight (and thumbnail, if also still pending) are marked unavailable, not the whole part.
- What happens when a part's file is an STL? The system slices it against a fixed internal generic default material (there being no material to parse from a bare mesh) and stores the resulting filament requirement as fully unconstrained ("any material," FR-002a) — this is the normal, expected outcome for this format, not a rejection case, and it's the only file type this can happen for.
- What happens when a file requires slicing but no registered printer has a Machine Profile linked yet? The add or replace is rejected — automatic slicing has nothing to target until at least one printer has one linked.
- What happens when automatic in-app slicing is still running for an add or replace request? The system shows a clear in-progress state. Once nozzle diameter and material resolve, the operator may confirm/save even though estimated print time/weight and thumbnail(s) may still be resolving (FR-009c) — nothing is visible in the catalog until the operator actually confirms, regardless of which fields have finished by then.
- Does an already-sliced file's add/replace show the same in-progress state? Yes — it goes through the identical processing → ready-for-review step, it simply resolves near-instantly in practice since parsing embedded metadata needs no external process, so every field (including estimate/thumbnail) is typically ready together; an operator may still briefly see a processing indicator before the review step appears.
- What happens if an operator tries to confirm/save a new part before nozzle diameter/material have resolved, or before entering a name? The confirm action is unavailable until both conditions are met — there is no way to force-save early on those two values, and no way to leave the name blank; the operator can still freely edit the name/tags while waiting, just not submit them, until nozzle diameter/material resolve. Estimated print time/weight and thumbnail are not part of this gate (FR-009c).
- What happens when a slice reaches "ready for review" but the operator discards it instead of confirming? Nothing is saved — for an add, no part is created; for a replace, the part's existing file and data remain exactly as they were, identical to a slicing failure's outcome except the slice itself succeeded.
- What happens when an operator confirms/saves a part before its estimated print time/weight or thumbnail have finished resolving? The part is created/updated immediately with nozzle diameter and material set; print time/weight/thumbnail show as "still resolving" until the background work completes, at which point they update onto the part in place, pushed to the operator's view over the same real-time channel used elsewhere (FR-009e) — no manual refresh needed.
- What happens when a Filament Profile/color-variant an operator used to narrow one of a part's filament requirements is later deleted from the Phase 2/3 catalog? That requirement's narrowing reference becomes unresolved and is surfaced as such, but it (and the part as a whole) continues matching on its parsed generic material type and the part's nozzle diameter alone — the other requirements on the same part are unaffected.
- What happens when an operator deletes a part? Its file and all derived data are deleted with it, since nothing in this phase (no Job entity yet) references a part's data independently of the part itself.
- What happens when an operator tries to add a part with no file at all? The system rejects it — a part must have exactly one file to exist.
- What happens when a thumbnail cannot be derived for one or more of a part's plates (e.g. no embedded preview image present)? The part is still saved, just with those plates showing no thumbnail — this never blocks saving, unlike the part's nozzle-diameter/material data.
- What happens when two operators upload a replacement file for the same part at the same time? The system applies one replacement and rejects the conflicting concurrent one rather than corrupt the part's file or derived data.
- What happens when an operator wants the same design available for two different nozzle-diameter targets simultaneously? Not supported on a single Part — they must create a separate Part record for each target they want to keep at once.
- What happens when the farm's registered printers are evenly split between two nozzle diameters (no single most-common value)? The system picks one deterministically (e.g. the smaller diameter, or whichever a stable tiebreak rule selects) rather than failing or asking the operator — the exact tiebreak rule is a planning-level detail.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST allow operators to add a part with a name and exactly one file (STL, 3MF, or G-code). A thumbnail image is automatically derived from the file (FR-014) rather than manually supplied. Attaching the file begins processing immediately — no material selection gates the start of processing, since no operator-supplied material exists anywhere in this flow (FR-002). The name (along with tags, FR-015) MAY be entered or changed at any point while processing runs and is only actually required at the confirm/save step (FR-009a/FR-009b), not before processing can start.
- **FR-002**: System MUST NOT accept an operator-supplied Filament/material on the Add or Replace request, for any file type. The generic material type used as the automatic in-app slicing target MUST instead be resolved directly from the file's own content: for a 3MF that requires slicing (an unsliced project file), by parsing the project's own filament assignment (present because Orca Slicer/Bambu Studio require selecting one before a project can be saved at all); for a file that does not require slicing (G-code, or an already-sliced 3MF), material is parsed from its embedded slice metadata as already specified (FR-012), independent of this requirement. An STL carries no material data by construction — FR-002a governs that case specifically. The operator's only material-related input anywhere in this phase is narrowing an already-derived filament requirement to a specific Filament Profile/color-variant at the review/confirm step (FR-012a), after the real result is known.
- **FR-002a**: System MUST treat an STL's automatic in-app slice as targeting a fixed, internal, non-operator-configurable generic default material — since a bare mesh can never carry material data of its own — and MUST store the resulting filament requirement as fully unconstrained (no material type recorded). This is the *only* file type/scenario that produces a fully unconstrained requirement: an unsliced 3MF's parsed project-level material (FR-002) is always a real generic type (e.g. "PETG"), never treated as unconstrained, and if it cannot be parsed the add/replace is rejected outright (FR-006) rather than falling back to this case. The resulting estimate for an STL-sourced part is a best-effort approximation, not a guarantee accurate for whatever material the part is eventually printed in; the part remains complete (FR-006) even though its estimate may not be. This "any material" behavior MUST NOT apply to an already-sliced file, whose process parameters are physically fixed to one specific material once sliced (FR-006, FR-012a).
- **FR-003**: System MUST determine, for the file attached to a part, whether it requires slicing: an STL file MUST always be treated as requiring slicing, a G-code file MUST always be treated as not requiring slicing, and a 3MF file's status MUST be determined from its own embedded metadata (whether it already contains sliced G-code/toolpath data).
- **FR-004**: System MUST treat every file upload for an existing part as a direct replacement of its current file — a part holds exactly one file at any time, never more. If the new file fails to process (FR-006), the replacement MUST be rejected and the part's existing file and derived data MUST remain completely unchanged.
- **FR-005**: System MUST automatically invoke a headless slicer engine against a part's file whenever it requires slicing (on initial add or after a replacement), targeting the material resolved per FR-002 (an unsliced 3MF's parsed project-level material) or FR-002a (an STL's fixed internal generic default), and the nozzle diameter most common among the farm's currently-registered printers (FR-005a) — successfully deriving nozzle diameter, generic material type, estimated print time, estimated filament weight, and a rendered thumbnail. A successful slice's derived data MUST be presented to the operator for review (FR-009a) rather than saved directly. The slicer's toolpath output itself MUST NOT be persisted, and the part's file MUST remain exactly as uploaded.
- **FR-005a**: System MUST determine the nozzle diameter to slice against by reading, for each registered printer that has a Machine Profile (Phase 2) linked, that profile's nozzle size, and selecting whichever nozzle diameter is most common among those printers — with no operator input and no organization-level configuration involved. A printer with no Machine Profile linked does not count toward this determination.
- **FR-005b**: System MUST allow an operator to link a registered printer to a Machine Profile (Phase 2) at any time after the printer is created — this link is optional at printer-creation time (a matching profile may not have been imported yet) but is what makes that printer count toward FR-005a's nozzle-diameter determination.
- **FR-006**: System MUST reject an add or replace operation outright — never saving a part with unresolved nozzle diameter or material — whenever: (a) the file requires slicing and no registered printer has a Machine Profile linked (so no nozzle diameter can be determined), (b) an unsliced 3MF's project-level material assignment cannot be parsed, or (c) an already-sliced file's nozzle diameter, material type, or estimate cannot be parsed. There is no manual-entry fallback for any of these values, and no operator override that avoids them (FR-002). An STL never hits case (b) — it has no project-level material to fail to parse; FR-002a's fixed internal default always succeeds for it. A background slicing failure (engine error, timeout, unsupported/non-manifold geometry) that occurs **before** the operator has confirmed still rejects the operation outright, exactly as before; if it occurs **after** an early confirmation (FR-009d), the part remains saved with its estimate marked unavailable instead of being rejected — see FR-009c/FR-009d for the deferred-estimate case this carves out of the "never incomplete" rule.
- **FR-007**: System MUST allow an operator to configure, at the organization level, only a default slicer engine (OrcaSlicer or Bambu Studio) used for automatic in-app slicing whenever a part-specific override isn't given — no other slicing-target setting is organization-configurable.
- **FR-008**: System MUST allow an operator to override the slicer engine for one specific part's automatic slice, without altering the organization-wide default used elsewhere.
- **FR-009**: System MUST process every add/replace request — whether the file requires slicing or is already sliced — as an asynchronous background operation: the request MUST NOT block on the result, and the system MUST surface a clear in-progress ("processing") state while it runs. This applies uniformly regardless of file type; an already-sliced file typically resolves near-instantly in practice (parsing embedded metadata needs no external process), but goes through the identical shape as a file requiring slicing rather than a separate synchronous path.
- **FR-009a**: System MUST hold every successfully-processed result — however it was produced, by parsing an already-sliced file's own metadata or by an in-app slice — in a "ready for review" state, presenting whatever has been derived so far. Nozzle diameter and generic material type(s) MUST always be present by the time "ready for review" is reached (FR-006 blocks on them). Estimated print time/weight and the thumbnail MAY still be pending at this point for a file requiring slicing (FR-009c) — when pending, the review presents them as "still resolving" rather than a value. The operator MUST be able to (a) optionally attach or change a narrower Filament Profile/color-variant override for any one of the resulting filament requirement(s) (FR-012a) and then confirm, which saves the part (creating it, or applying the replacement) immediately from whatever has already been derived — not waiting on any still-pending value (FR-009c/FR-009d) — or (b) discard the reviewed result, in which case nothing is saved — for an add, no part is created; for a replace, the part's existing file and data are unaffected. Neither path allows editing the derived nozzle diameter, material type, or estimate values themselves (FR-006/FR-013 — those remain fully derived, never hand-entered).
- **FR-009b**: System MUST allow an operator to enter or change a new part's name and tags at any point while its file is processing, concurrently with FR-009's in-progress state — these are not gated behind processing completion. The confirm action (FR-009a) MUST be unavailable (e.g. a disabled Save control) until both conditions hold: nozzle diameter and material have resolved (not the full "ready for review" state's every field — FR-009c), and, for a new part, a name has been entered; confirming submits the name/tags together with any narrower filament overrides in the same action. Replacing an existing part's file follows the identical shape, without name/tags (FR-004 — unaffected by a replace).
- **FR-009c**: System MUST allow an operator to confirm/save a part as soon as its nozzle diameter and material are resolved (FR-002/FR-002a/FR-005a) and, for a new part, a name has been entered — without waiting for estimated print time, filament weight, or the thumbnail to finish resolving. For an already-sliced file, all of these values are typically available together (parsing is near-instant), so this rarely creates a visible gap in practice; for a file requiring slicing, nozzle diameter and material are resolved *before* the slicer even runs (they are slicing inputs, not outputs — FR-005), so this is the file-requiring-slicing case's normal path to an early save. An operator who instead keeps the dialog open past that point continues to see progress, with estimated print time/weight and the thumbnail appearing before they confirm, exactly as this feature behaved before FR-009c — confirming early is an option, not a requirement.
- **FR-009d**: If an operator confirms/saves before estimated print time/weight or the thumbnail have finished resolving, System MUST create/update the part immediately with nozzle diameter and material set, and print time/weight/thumbnail marked as still resolving. Once the background work completes, System MUST update the saved part's print time/weight/thumbnail in place. If that background work subsequently fails, System MUST leave the part saved with its print time/weight/thumbnail marked as unavailable — never blocked, rolled back, or flagged as needing reprocessing. This is the one case in this phase where a part may permanently carry incomplete derived data; nozzle diameter and material remain always-required and still reject the operation outright if they cannot be resolved (FR-006).
- **FR-009e**: System MUST notify the operator's view of a part's print time/weight/thumbnail arriving or permanently failing after an early save through the same real-time channel used for every other live update in this feature — no view in this feature relies on the operator manually refreshing to see this update.
- **FR-010**: System MUST implement in-app slicing — engine invocation given a file requiring slicing plus a target material and nozzle diameter, producing nozzle diameter, material type, estimated print time/weight, and a thumbnail — as a capability reusable outside this phase's own automatic-at-upload trigger, so Phase 7 (Jobs) can later invoke it on-demand at job-dispatch time to produce actual sliceable output for a job's specific target printer, without rebuilding the slicing integration. This phase itself builds only the automatic-at-upload trigger (FR-005) — no job-dispatch-time trigger exists yet, since no Job entity does.
- **FR-011**: System MUST parse nozzle diameter directly from a part's file when that file does not require slicing, and store it as the part's machine-compatibility requirement, matching any printer sharing that value. There is no concept of linking a part to a specific Machine Profile record, and no filament-diameter matching in this phase.
- **FR-012**: System MUST parse the generic material type directly from a part's file when that file does not require slicing, by scanning **every plate and every AMS slot within each plate** the file's embedded metadata declares for its detected material type and color, then **grouping the results by distinct (material type, color) pairs** — producing exactly one filament requirement per distinct pair (a single requirement for a single-material file; one per distinct pair for an AMS-style multi-color mapping and/or a multi-plate file with different materials per plate; repeated pairs across multiple plates/slots do not produce duplicate requirements), each matching any spool/filament of its generic material type by default. Detected color is used only to group/distinguish requirements from each other — it is never itself a matching criterion. A file requiring slicing always produces exactly one filament requirement, since in-app slicing targets exactly one resolved material (FR-002/FR-002a) — true multi-material in-app slicing (assigning different materials to different regions of one model) is out of scope for this phase.
- **FR-012a**: System MUST allow an operator to optionally narrow any one of a part's filament requirements to a specific Filament Profile (Phase 2) or Filament catalog color-variant (Phase 3), overriding that requirement's generic-type default when an exact brand/color match matters (e.g. one distinct color-group of a multi-color/multi-plate file) — independently of any other requirement on the same part. Because each requirement already represents every plate/slot sharing its (material type, color) pair (FR-012), narrowing it applies uniformly to all of them — there is no separate per-plate or per-slot narrowing beneath that grouping.
- **FR-013**: System MUST derive estimated print time and filament weight for every part — parsed directly from its file when that file does not require slicing, or from the automatic in-app slice when it does. For a file that does not require slicing this remains a required condition of reaching "ready for review" (FR-006); there is no manual-estimate fallback. For a file requiring slicing, this value MAY still be resolving at the moment the operator confirms/saves (FR-009c/FR-009d) — it is not a blocking condition on save for that case, only on "ready for review" eventually reaching a complete state. For an already-sliced multi-plate file, each estimate is the **sum across every plate**, since the file executes all of its plates as one continuous physical print.
- **FR-014**: System MUST automatically derive a thumbnail image for every plate in a part's file, not only the first: for a file requiring slicing, by rendering a preview of each plate as part of the in-app slicing pass (MAY still be resolving at confirm time, per FR-009c/FR-009d); for an already-sliced file (G-code, or a 3MF that already contains one), by extracting each plate's own embedded preview thumbnail image. The Part's single catalog/list-view thumbnail remains the first plate's image; the full per-plate set is presented in the part's own review/detail view. A derived thumbnail MUST be normalized to a single standard image format so no per-plate image-format tracking is needed.
- **FR-014a**: Failure to derive a thumbnail MUST NOT block adding or replacing a part — a part MAY exist with no thumbnail (for one, several, or all of its plates), unlike its nozzle-diameter/material data, which MUST be successfully derived before "ready for review" (FR-006). Unlike thumbnail, estimated print time/weight (FR-013) is required before "ready for review" for a file that does not require slicing, but — like thumbnail — MAY remain unresolved/unavailable indefinitely for a file requiring slicing that was confirmed early (FR-009d).
- **FR-015**: System MUST allow operators to tag parts with one or more reusable tag values (category, product line, etc.) and filter the catalog by tag.
- **FR-016**: System MUST allow a part to be added, browsed, tagged, and have its file replaced, with no live printer connection — catalog and slicing operations in this phase never require a live printer connection, though FR-005a does require read access to the printer catalog's Printer-to-Machine-Profile links.
- **FR-017**: System MUST record part creation, file replacements (automatic and manual), a discarded reviewed slice, and organization slicer-engine default changes in the activity log, including who/what made the change and when.
- **FR-018**: System MUST reject adding a part with no file.

### Key Entities

- **Part**: A reusable catalog entry representing something an operator prints repeatedly. Key attributes: name, an automatically-derived, per-plate set of thumbnail images (any of which may be absent if derivation wasn't possible; the first plate's image is the catalog/list-view thumbnail), tags, exactly one File, one or more Filament Requirements (see below — possibly a single fully-unconstrained "any material" requirement, FR-002a, when the File is an STL), nozzle diameter (always present once saved — FR-006), and estimated print time/filament weight. Nozzle diameter and material are always resolved before a Part can be saved (FR-006) — there is no manual numeric entry and no partial state for either. Estimated print time/weight, by contrast, MAY be "still resolving" at the moment the Part is saved, for a File requiring slicing that the operator confirmed early (FR-009c/FR-009d); it updates in place once the background slice completes, or is left permanently marked unavailable if that background work fails. Distinct from a Job (Phase 7), which doesn't exist yet, and from an Assembly (Phase 6), which is how multiple Parts get combined — a Part itself never holds more than one file's worth of content, and never links to a Machine Profile.
- **Filament Requirement**: One of a Part's one-or-more material needs — a generic material-type requirement (e.g. "PETG") plus an optional narrower override to a specific Filament Profile/color-variant. An already-sliced file with a single material produces exactly one; one with an AMS-style multi-color mapping and/or multiple plates using different materials produces one **per distinct (material type, color) pair** found across every plate/slot in the file — detected color groups/distinguishes requirements but is never itself a matching criterion, and narrowing one requirement applies to every plate/slot sharing its pair. A file requiring slicing always produces exactly one, targeting the single material resolved for the in-app slicing target (FR-002/FR-002a) — never an operator-supplied choice at upload time.
- **File**: The single file attached to a Part — STL, 3MF, G-code, or a brand-specific bundle — always persisted exactly as uploaded. Determined, at the time it's uploaded, to either **require slicing** (an STL, or a 3MF without embedded sliced G-code) or **not require slicing** (a G-code file, or a 3MF that already contains sliced G-code/toolpath data). A 3MF requiring slicing also carries its own project-level filament assignment (FR-002), always expected to be parseable — unlike an STL, which never carries one. Uploading a new file for a part always replaces the current one — there is never more than one at a time, and a failed replacement leaves the existing file and data completely untouched.
- **Tag**: A reusable label (category, product line, etc.) an operator can apply to any number of Parts to organize and filter the catalog.
- **Slicing Defaults (Organization Setting)**: An organization-level configuration naming only the default headless slicer engine (OrcaSlicer or Bambu Studio) used for automatic in-app slicing whenever a part doesn't override it. A part-specific slice request may override the engine for that request only, without changing the stored organization default. Holds no nozzle-diameter, filament-diameter, or material configuration — those are either auto-detected (nozzle diameter, from the printer catalog) or explicitly supplied per part (material).
- **Printer ↔ Machine Profile link**: This phase wires the previously-deferred link between a fleet `Printer` (Phase 1) and a Machine Profile (Phase 2) — the linkage Phase 1's own dependency notes earmarked for "whichever later phase actually consumes it." The link is optional per printer (a matching Machine Profile might not be imported yet), set independently of printer creation. A printer with one linked is treated as a "real fleet member" for FR-005a's nozzle-diameter auto-detection; a printer without one simply doesn't count toward it.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An operator can add a new part from a file requiring slicing in under 2 minutes — nozzle diameter and material resolve automatically (no manual entry, no organization configuration, and, since FR-002 removes it, no material selection required beforehand), letting the operator save well before a large file's estimate/thumbnail necessarily finishes resolving.
- **SC-002**: An operator can add or replace a part's file with an already-sliced one and have it fully described (parsed data + thumbnail) in under 1 minute.
- **SC-003**: 100% of parts that exist in the catalog have **complete** nozzle-diameter/material data — since a part is never saved without it (FR-006). Estimated print time/filament weight is complete for every part sourced from a file that doesn't require slicing, and eventually complete for the large majority of parts sourced from a file requiring slicing — except (a) a part confirmed early (FR-009c/FR-009d) whose deferred slice later fails, which permanently shows its estimate as unavailable, and (b) an STL-sourced ("any material," FR-002a) part, whose eventual estimate is a best-effort approximation against a fixed internal placeholder material, not a guarantee of the part's actual eventual print time/weight. Nozzle-diameter/material completeness is unconditional; estimate completeness and accuracy are not, for these two named cases.
- **SC-004**: A part's derived nozzle-diameter/generic-material match is broad by construction — any printer and any spool/filament sharing those values qualifies, with zero duplicate parts needed solely because two printers share a nozzle diameter, or two spools share a generic material.
- **SC-005**: An operator can filter a catalog of 500+ parts down to a relevant subset by tag in under 10 seconds.
- **SC-006**: At least 90% of files requiring slicing, added with at least one printer registered, slice successfully on the first attempt — the remainder either are rejected clearly (if the failure occurs before the operator confirms) or leave an already-saved part with its estimate marked unavailable (if the failure occurs after an early confirmation, FR-009d) — never saved with a plausible-looking but wrong estimate either way.
- **SC-007**: An automatic in-app slicing failure occurring before the operator has confirmed never leaves a partially-created or corrupted part — 100% of such failures result in a clean rejection (or, for a replace, no change at all) with nothing incomplete ever saved. A failure occurring after an early confirmation (FR-009d) is the one exception: the part itself remains saved and valid (nozzle diameter/material intact), only its estimate is marked unavailable.
- **SC-008**: A part created directly from an already-sliced file becomes fully usable exactly as immediately as one produced via automatic in-app slicing — no functional gap between the two paths.
- **SC-009**: At least 90% of successfully-saved parts have a real, non-blank thumbnail for at least their first plate, automatically derived from their file, with no manual image upload ever required.

## Assumptions

- **A Part holds exactly one File, never a collection.** There is no "source model" concept and no notion of multiple already-sliced variants coexisting on the same Part (e.g. one per nozzle-diameter target) — Assembly (Phase 6) is the mechanism for combining multiple distinct parts, so a Part itself stays deliberately atomic. Running the same design against more than one nozzle-diameter/material combination at once requires separate Part records.
- **A 3MF that bundles multiple plates/objects internally is treated as one indivisible file belonging to one Part**, but is no longer reduced to a single thumbnail — every plate now gets its own derived thumbnail (FR-014), with only the first plate's image used for the catalog/list-view thumbnail. The system still does not attempt to split the file, warn about multi-plate content as such, or create more than one Part from it — that remains an accepted, unaddressed limitation; only the thumbnail and filament-requirement handling have been reopened.
- **A part is never saved without a resolved nozzle diameter and material.** These are always successfully derived (parsed directly, for a 3MF/G-code; or resolved as the slicing input, for a 3MF's project-level assignment or an STL's fixed internal default) before an add or replace operation completes; a failure to resolve either (unparseable 3MF material, no known printer nozzle diameter) rejects the whole operation rather than saving a partial result. There is no manual numeric entry anywhere for either value. **Estimated print time/weight and the thumbnail are treated differently**: for a file that doesn't require slicing they resolve at the same moment as nozzle diameter/material (parsing is near-instant) so this distinction is rarely visible in practice; for a file requiring slicing, the operator MAY confirm/save as soon as nozzle diameter/material are known, before these finish resolving (FR-009c) — in which case they update onto the already-saved part once ready, or are left permanently marked unavailable if the deferred slice fails (FR-009d). This is the one legitimate way a part can carry incomplete derived data in this phase.
- **Every add/replace, regardless of file type, has a "ready for review" state between a successful process (parse or slice) and the part actually being saved.** This applies uniformly to already-sliced and requires-slicing files alike — there is no longer a separate one-step synchronous path for an already-sliced file. Both a G-code/already-sliced-3MF upload and an STL/unsliced-3MF upload go through the identical submit → processing → ready-for-review → confirm/discard shape; only the underlying mechanism differs (reading embedded metadata vs. invoking an external slicer), and only that difference — not the operator-facing flow — determines how long "processing" takes (typically near-instant for an already-sliced file). Reaching "ready for review" no longer implies every field has finished resolving (FR-009a) — nozzle diameter/material are always present by then, but estimated print time/weight and the thumbnail may still show as "still resolving" for a file requiring slicing; confirming at that point is a legitimate operator choice (FR-009c), not a workaround.
- **A Part's filament requirement is a collection, not a single value.** A single-material file (sliced or already-sliced) produces exactly one filament requirement; an already-sliced file with a real AMS-style multi-color mapping and/or multiple plates using different materials produces one requirement per **distinct (material type, color) pair** detected across every plate and slot in the file — not one per slot/plate individually, so repeated pairs (e.g. two plates both black PETG) collapse into a single requirement rather than duplicating. Each requirement has its own generic material type and independently-optional narrower override, which applies to every plate/slot sharing that requirement's pair. In-app slicing itself still only ever targets one resolved material per slice (FR-002/FR-002a; true multi-material *slicing* — different materials for different regions of one model — is out of scope for this phase), so a requires-slicing part always ends up with exactly one requirement even though the data shape supports more.
- **A multi-plate 3MF's filament requirements and per-plate thumbnails are now both detected, even though the file itself is still never split.** Every plate (and every AMS slot within each) is scanned for its material/color, and every plate gets its own derived thumbnail (already-sliced: extracted from that plate's own embedded preview; requires-slicing: rendered per-plate during in-app slicing) — only the catalog/list-view thumbnail stays pinned to the first plate. Estimated print time/weight are still the sum across all plates, since the file executes them as one continuous print. This reopens, for filament-requirement and thumbnail detection specifically, the earlier "accepted, unaddressed limitation" that a multi-plate 3MF is treated as one indivisible file; splitting the file into multiple Parts remains the one thing still out of scope.
- **There is no "job-ready" state.** Every part that exists is, by construction, fully valid and usable — there's nothing to flag as not-ready. The only remaining status distinction a part carries is whether its file requires slicing (Phase 7 will need to slice it again for real toolpath data at job-dispatch time, since nothing sliceable is persisted) or was already sliced on upload (its stored file can be sent to a printer directly).
- **A part's thumbnails are automatically derived from its file, never manually uploaded — one per plate, not just one per part.** For a file requiring slicing, each plate's preview is rendered as part of the in-app slicing pass (e.g. via a slicer CLI's per-plate preview export capability). For an already-sliced file, each plate's own embedded preview image is extracted — G-code embedding a base64 preview in comments, and Bambu-style `.gcode.3mf` embedding one per plate in its metadata, are both standard, widely-supported slicer/firmware conventions (used for printer on-device screens), so this is reliably available for already-sliced files too. Deriving a thumbnail is best-effort only, per plate — unlike nozzle-diameter/material data, a missing thumbnail (for one, several, or all plates) never blocks saving the part. **Whatever source format a derived/extracted thumbnail arrives in, the system normalizes it to one standard image format at save time** — a thumbnail is always an image, so there is no need to separately track each thumbnail's original format/content-type.
- **There is no concept of linking a part to a specific Machine Profile.** A part's machine compatibility is expressed purely through its derived nozzle diameter. The optional narrower link to a specific Filament Profile/color-variant (for exact brand/color matching) is unaffected by this and still supported.
- **Filament-diameter matching is dropped from this phase entirely.** The modern desktop-printer market this project targets is virtually uniform at 1.75mm, and printer telemetry doesn't naturally expose it, so tracking it isn't worth the added printer-catalog work. Only nozzle diameter and generic material type gate compatibility.
- **There is still no organization-configured default material, and now no per-request operator-supplied material either** — an operator/organization can never set one via Settings, and `filamentId` no longer exists on the Add/Replace request at all (FR-002). The system resolves material purely from the file: a 3MF's own project-level filament assignment when it requires slicing, or its embedded slice metadata when it doesn't. Only an STL — which can carry neither — falls back to a **fixed, internal, non-operator-configurable** generic material (FR-002a) purely to run the immediate in-app slice; this remains a system-level implementation default for that one format-specific case, never an organization-configurable setting, and it never appears as a Settings field anywhere.
- **Nozzle diameter for automatic slicing is auto-detected from the farm's registered printers, not configured.** Specifically, the value most common among printers that have a Machine Profile linked is used, with no operator input and no organization-level Settings field for it. **This phase resolves its dependency on the printer catalog (Phase 1) by finally wiring the Printer ↔ Machine Profile link that `docs/FEATURE_PLAN.md`'s own Phase 1 dependency notes already earmarked for "whichever later phase actually consumes it"** — nozzle diameter is read from a printer's linked Machine Profile (Phase 2, which already models nozzle size), not a new duplicate field on `Printer`. The link is optional at printer-creation time (a matching Machine Profile might not be imported yet), so a printer can exist without one; only a printer with one linked counts as a "real fleet member" for this determination (FR-005a/FR-005b). If no registered printer has a Machine Profile linked, automatic slicing — and therefore adding or replacing a part whose file requires slicing — is rejected (FR-006) until at least one does.
- This auto-detected nozzle diameter is purely Phase 4's own slicing-target heuristic. It is explicitly distinct from real job/printer matching at dispatch time (Phase 7), which will depend on which printers and feed-slot materials are actually available at that later moment, not on this phase's one-time slicing choice.
- **Uploading a new file for an existing part is always a direct, destructive replacement, and it either fully succeeds or changes nothing.** There's no staleness flag and no versioned file history; a failed replacement leaves the part's prior file and derived data completely untouched rather than partially updated.
- **A job already queued or printing (Phase 7) is unaffected by a part's file being replaced afterward, by construction of the two phases together rather than anything this phase itself needs to build.** Per `docs/FEATURE_PLAN.md`'s Phase 7 section, a job locks onto a copy/reference of the print-ready content it needs at queue time (whether that's the part's stored already-sliced file, or a fresh on-demand slice Phase 7 itself produced), not onto "whatever the part's file currently is." No FR in this phase exists for this specifically — it's a requirement on Phase 7's own job-locking design, noted here for traceability.
- This phase covers catalog data only — a part and its tags — with no interaction with a live printer connection or an actual print job; those come in Phase 7 (Jobs) and later phases. In-app slicing itself needs no live printer connection either — only the part's file, the specified material, the auto-detected nozzle diameter, and the configured slicer engine/CLI.
- A part's derived print data (nozzle diameter, generic material type) requires no dependency on the Phase 2 profile catalog beyond the Filament itself (already required per FR-002) — it's either parsed straight from an already-sliced file or produced by a slicing pass. Phase 2 (Profiles — machine + filament, imported from slicer bundles, `specs/003-slicer-profile-import`) is only additionally needed for the optional narrower Filament Profile/color-variant override.
- **This phase merges the former Phase 23 — In-app slicing into Phase 4**, since a file requiring slicing carries none of the parseable time/weight/nozzle metadata FR-011/FR-012/FR-013 depend on — only an actual slicing pass produces it. `docs/FEATURE_PLAN.md` is updated accordingly to fold Phase 23's scope into Phase 4 and renumber the former Phase 24 down to Phase 23.
- Every add/replace — in-app slicing or already-sliced-file parsing alike — executes as an asynchronous background operation (per this project's constitutional rule that long-running work never blocks a request thread, and per the unified Processing → Ready for Review shape both paths now share); a successful result reaches a "ready for review" state rather than committing directly, and notifies the operator of that (or of a failure) through the same real-time channel other live updates already use. The part is only actually created/updated once the operator explicitly confirms the reviewed result (FR-009a).
- OrcaSlicer is the built-in default engine when no organization Settings override exists yet, given its open-source (GPLv3) licensing and the broader printer/profile support Phase 2's import flow already relies on.
- A file requiring slicing is assumed to be a clean mesh/project export, not another slicer's fully-baked project file, so it's assumed not to carry another slicer's project-level settings/metadata. The documented OrcaSlicer/Bambu Studio cross-compatibility gaps (one rejecting or partially loading the other's saved project `.3mf`) are therefore not a blocker for feeding it into whichever engine is configured; that risk applies only to a manually-uploaded, already-sliced file produced externally by a specific slicer, which this phase's parsing (FR-011/FR-012/FR-013) treats as metadata to scan rather than a project file to fully reopen.
- Running a headless slicer engine (OrcaSlicer and/or Bambu Studio CLI) is a new external infrastructure/tooling dependency this phase introduces — installed and invoked from the backend — distinct from anything Phase 0–3 needed.
- **3MF requires-slicing/already-sliced disambiguation (FR-003)** is based on the file's own embedded metadata — specifically, whether it contains actual sliced G-code/toolpath data and the slicing-result metadata produced alongside it (e.g. Bambu's `Metadata/slice_info.config`, which only exists in an already-sliced `.gcode.3mf`, versus an unsliced project/mesh 3MF which lacks it). An uploaded STL can never be ambiguous this way (STL has no capacity to embed toolpath data at all), and a plain `.gcode` file is unambiguously always already-sliced (there's no "unsliced" form of a G-code file).
