# Feature Specification: Phase 4 — Part Library (with Sliced Files & In-App Slicing)

**Feature Branch**: `[007-part-library]`

**Created**: 2026-07-19

**Status**: Draft

**Input**: User description: "Phase 4"

## Clarifications

### Session 2026-07-19

- Q: How should a part declare its filament requirement, given PETG-sliced files should match any PETG spool by default unless narrowed to a specific brand/color? → A: Generic type + optional override — store the generic material type (e.g. "PETG") parsed directly from the `filament_type` metadata as the baseline match; operator may optionally attach a specific Filament Profile/color-variant to narrow matching to an exact brand/color.
- Q: How should a part declare which printers it's physically compatible with, given it should be printer-agnostic but nozzle-size-aware? → **Revised below** — filament-diameter matching is dropped entirely; see the later clarification on nozzle-diameter auto-detection.
- Q: Given estimated print time and filament usage are reliably embedded in already-sliced file metadata, how should the system use the parsed values? → A: Auto-parse, authoritative — parse and store the value directly with no operator review step.
- Q: Should this phase flag a part's file as potentially stale in some way? → A: No — deferred out of this phase entirely (per direct instruction, not a formal question). There's no staleness concept to build; replacing a part's file is a direct, immediate replacement, not a flag-and-decide-later workflow.
- Q: Phase 23 (In-app slicing) is being merged into this phase, since a raw/unsliced file has no parseable time/weight/nozzle metadata until something actually slices it — should manually uploading an already-sliced file remain supported alongside automatic in-app slicing? → A: Both paths supported — an operator can upload a file requiring slicing (system automatically invokes a headless slicer CLI) or upload an already-sliced file directly.
- Q: Which headless slicer engine should in-app slicing invoke — OrcaSlicer, Bambu Studio, or both? → A: Configurable default with per-part override — an organization-level Settings option sets the default engine (OrcaSlicer recommended: open-source, broadest printer support, already the Phase 2 import source), and each part's in-app-slicing request pre-fills that default but lets the operator pick a different engine for that specific request.
- Q: When does in-app slicing actually run — on an operator-invoked "pick a machine profile, slice now" request, or automatically at specific trigger points? → A: Automatically, whenever a part's file requires slicing (initial upload or a replacement upload) and the part has a material available. This phase builds only this automatic-at-upload trigger and the reusable in-app-slicing capability itself; a separate future on-demand trigger at job-dispatch time (Phase 7, once a Job entity exists) is a forward-compatibility note, not built here.
- Q: Is uploading a new file for a part additive or a direct/destructive replacement, and what happens to a job already in the queue (Phase 7) either way? → A: A part holds exactly one file, so every upload after the first is necessarily a replacement, never additive. A queued/printing job is unaffected either way: Phase 7's job design (`docs/FEATURE_PLAN.md`) locks a job onto a copy/reference of the print-ready content it needs at queue time, not onto "whatever the part's file currently is."
- Q: Should a Part hold a flat collection of multiple Files, or exactly one? → A: **Exactly one, always.** Given Assembly (Phase 6) already exists to combine multiple parts, a Part itself stays atomic — strictly one file per part, period. A 3MF that happens to bundle multiple plates/objects is still treated as one indivisible file belonging to one Part — the system does not detect, split, or warn about multi-plate 3MF content; an accepted, unaddressed limitation.
- Q: Should the system persist an actual sliced-output file when it auto-slices an STL/3MF, or only the derived estimate/matching data? → A: **Only the derived data — never a persisted sliced-output file, unless the upload itself already was one (G-code).** Automatic in-app slicing of an STL/3MF is purely to derive nozzle diameter, generic material type, estimated print time, and estimated filament weight, which are stored directly on the Part; the slicer's actual output is discarded.
- Q: Should a part ever exist with a Machine Profile explicitly linked to its file? → A: **No — dropped entirely.** A part's compatibility is expressed purely through its derived nozzle diameter; there is no concept of linking a part to a specific Machine Profile record. (An optional narrower link to a specific Filament Profile/color-variant, for exact brand/color matching, is unaffected and still allowed.)
- Q: Should an unparseable already-sliced file, or a file requiring slicing with no material available, ever be saved with manual-fallback estimates — or must every part have real, derived data before it can be saved at all? → A: **No manual fallback of any kind — a file must be fully parseable/sliceable before the part it belongs to can be saved.** If an already-sliced file's nozzle diameter, material type, or time/weight can't be parsed, the add/replace is rejected outright. If a file requires slicing and no material is available, the add/replace is also rejected — it is never saved in a pending or partial state. There is no manual numeric entry for nozzle diameter, print time, or filament weight anywhere in this phase.
- Q: Given every saved part now always has complete, derived data, is a separate "job-ready" / "not yet job-ready" concept still needed? → A: **No — dropped entirely.** Every part that exists is, by construction, fully valid and usable — there's nothing to flag as "not ready." The only remaining distinction a part carries is whether its file **requires slicing** (meaning Phase 7 will need to slice it again for real toolpath data at job-dispatch time, since no sliceable output is persisted) or was **already sliced** on upload (meaning its stored file can be sent to a printer directly).
- Q: Should a part's thumbnail still be manually uploaded, or derived automatically from its file? → A: **Derived automatically, not manually uploaded.** For a file requiring slicing, the thumbnail is rendered from the model as part of the in-app slicing pass. For an already-sliced file (G-code, or a 3MF that already contains one), the thumbnail is extracted from its embedded preview image — G-code embedding a base64 preview image in comments, and Bambu-style `.gcode.3mf` embedding one in its metadata, are both standard, widely-supported slicer/firmware conventions (used for on-device screen previews), so this is reliably available for already-sliced files too. For a 3MF bundling multiple plates, only the first plate's image is used. Deriving a thumbnail is best-effort — failure to produce one does not block saving the part, unlike its nozzle-diameter/material/estimate data, which must succeed.
- Q: Should there be an organization-configured default material that automatic slicing falls back to when a part doesn't specify one? → A: **No — dropped entirely.** There is no organization default material. An intended Filament Profile is REQUIRED from the operator whenever a part's file requires slicing (no fallback exists); everything else follows the same two-tier pattern already established for filament matching — the operator either selects a Filament (matching any color/brand variant of that generic material, e.g. "Any PETG") or a specific filament variant (an exact brand/color), never a third "leave it unspecified" option for a file that needs slicing.
- Q: Should there be an organization-configured default nozzle diameter (and filament diameter) that automatic slicing targets? → A: **No — dropped entirely, and filament-diameter matching is dropped from this phase altogether** (it's a virtually-uniform 1.75mm across the modern desktop-printer market this project targets, and printer telemetry doesn't expose it anyway — not worth the catalog work to track). The only remaining organization-level Slicing Default is the default slicer **engine**. Nozzle diameter is instead **auto-detected from the farm's currently-registered printers**: automatic slicing targets whichever nozzle diameter is most common among them, with no operator input and no configurable setting involved. If the printer catalog has no registered printer with a known nozzle diameter yet, automatic slicing cannot proceed and the add/replace of a part whose file requires slicing is rejected until at least one exists. (Real job/printer matching at dispatch time — Phase 7 — will separately depend on which printers and feed-slot materials are actually available then; this auto-detected value is only Phase 4's own slicing-target heuristic, not that matching logic.)
- Q: Where does a printer's nozzle diameter actually come from, given Phase 1's `Printer` entity doesn't store it and this phase can't invent a new standalone data point? → A: **This phase finally wires the Printer ↔ Machine Profile link that `docs/FEATURE_PLAN.md`'s own Phase 1 dependency notes already earmarked for it** ("that linkage... stays deferred, until whichever later phase actually consumes it (Phase 4 — Part library)"). A printer's nozzle diameter is read from its linked Machine Profile (Phase 2, which already models `nozzle size`) — no duplicate field is added to `Printer` itself. The link is optional at printer-creation time (a matching Machine Profile may not have been imported yet), so a printer can exist without one; **only a printer with a Machine Profile linked counts as a "real fleet member" for nozzle-diameter auto-detection** — an unlinked printer simply doesn't contribute to the "most common nozzle diameter" calculation (FR-005a) or to FR-006's "at least one known nozzle diameter" check.
- Q: Should adding/replacing a part whose file requires slicing auto-save the moment the background slice succeeds, or should the operator review what was derived first? → A: **Review, then confirm** — the operator sees the derived nozzle diameter, material type, print-time/weight estimate, and thumbnail, may attach or change the optional narrower Filament Profile/color-variant override at that point (having now seen what was actually derived), and must explicitly confirm before the Part is created or its file is replaced. Discarding a reviewed result instead of confirming it is also supported — nothing is saved, exactly as if processing had never run. **This narrows, not reverses, the earlier "auto-parse, authoritative, no operator review step" answer**: that answer is still exactly true for the *numbers themselves* — there is still no manual entry or numeric override of nozzle diameter, material type, print time, or filament weight anywhere in this phase, at review time or ever. The only thing newly gated on operator action is *whether a successfully-derived result gets committed at all*, mirroring the Preview → Confirm shape Phase 2's slicer-bundle import already established (`specs/003-slicer-profile-import/`) for the same reason: a result the system itself produced (whether by parsing or by slicing — see the next clarification) is worth a look before it becomes permanent catalog data, even though nothing about the result itself is hand-edited. *(Superseded/broadened by the next clarification — initially scoped to the requires-slicing path only, now uniform across every file type.)*
- Q: Can a Part require more than one filament, to represent a real multi-color/AMS part sliced or pre-sliced with several distinct materials across different color slots? → A: **Yes — a Part holds a collection of filament requirements, not a single one.** Each requirement carries its own generic material type (e.g. "PETG") and its own optional narrower Filament Profile/color-variant override; an already-sliced file's own embedded multi-color mapping (e.g. a Bambu AMS slot assignment) is parsed into one requirement per detected slot, each independently narrowable. A file requiring slicing still targets exactly one operator-specified Filament per in-app slice (building true multi-material *slicing itself*, where different physical regions of one model get different materials, is out of scope for this phase) — an in-app slice therefore always produces exactly one filament requirement, though the operator may still attach its narrower override at the review/confirm step above. This supersedes the earlier single-`Filament`-per-Part framing throughout FR-002/FR-012/FR-012a and the Key Entities section.
- Q: Given a 3MF's already-sliced/requires-slicing status already has to be *classified* before it's known which processing path applies, and a G-code/already-sliced file's metadata still has to be *parsed* even though nothing external is invoked for it, should the review/confirm step really only apply to the requires-slicing path, or should every add/replace go through the identical Processing → Ready for Review → Confirm/Discard shape regardless of file type? → A: **Every add/replace goes through the same uniform pipeline, regardless of file format.** There is no longer a synchronous, direct-save branch for an already-sliced file: a G-code (or already-sliced 3MF) upload still reaches "processing" and then "ready for review" exactly like an STL/unsliced-3MF upload does — it simply resolves near-instantly in practice, since parsing embedded metadata takes no external process the way slicing does. The operator experience is identical in every case: submit, wait briefly for a result, review the derived nozzle diameter/material(s)/estimates/thumbnail (attaching narrower filament overrides at that point, for any file type, not only a slicer-derived one), then confirm or discard. **Why unify rather than keep the two-shape design**: the two paths already had to share almost everything (the same derived-data shape, the same rejection rules, the same thumbnail/estimate requirements, the same review/confirm mechanics for a multi-color already-sliced file) — the only real difference was *how* the result gets produced (an external slicer process vs. reading embedded metadata), which is exactly the kind of difference that belongs behind one interface's implementation, not exposed as two different API/UI shapes. This also removes the one place operators would otherwise need to learn two different interaction patterns for what is, from their point of view, the same action ("add a part from a file").
- Q: Does the operator have to finish filling out the whole add-part form (name, tags) before file processing can even begin, or can those details be entered while processing runs in the background? → A: **Attaching the file (plus a Filament pick, if the file needs slicing) starts processing immediately — name and tags are entered/finalized concurrently, while processing runs, and are only actually needed at the confirm/save step.** The add-part experience is one continuous form/dialog, not two separate round trips the operator has to consciously sequence: the moment a file (and, if required, a Filament) is attached, the system begins processing it in the background; the operator can keep typing the part's name, add tags, etc. in the same dialog while that runs. The Save action is disabled until processing reaches "ready for review" (and, for a new part, until a name has been entered) — once both are true, Save becomes enabled, submitting the name/tags/any narrower filament overrides together as the confirm step; Cancel at any point is the same as discarding. Replacing an existing part's file follows the identical shape, minus name/tags (unaffected by a replace).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Add and browse parts in the catalog (Priority: P1)

As a print farm operator, I want to add a part to a reusable catalog with one file and an intended material, so I have a single place to browse and manage everything I print — with a thumbnail and real compatibility/estimate data derived automatically, not entered by hand or configured up front.

**Why this priority**: This is the foundational catalog capability every other story in this phase builds on — a file replacement or tag all attach to a part that must exist first. It's independently valuable on its own: an operator gets a real, browsable product catalog with genuine data on every part, never a placeholder.

**Independent Test**: Can be fully tested by attaching one file (STL, 3MF, or G-code) that the system can successfully process — plus a Filament (generic or a specific variant), when the file needs slicing — confirming processing begins immediately while the name/tags remain freely editable, confirming Save stays disabled until both a name is entered and processing reaches "ready for review," then reviewing and confirming the resulting derived data, and confirming the part appears in the catalog with an auto-derived thumbnail and real nozzle-diameter/material/estimate data — via the identical attach → concurrently edit → review → confirm sequence regardless of which file type was uploaded.

**Acceptance Scenarios**:

1. **Given** no parts exist yet, **When** an operator adds a new part by attaching one file that requires slicing (STL, or an unsliced 3MF) along with a Filament (either a generic material like "Any PETG" or a specific filament variant), **Then** the system immediately begins automatically slicing it against the farm's most common nozzle diameter while the operator can still enter/edit the part's name and tags in the same dialog; once slicing succeeds the result is presented for review, and confirming (once a name has been entered) saves the part with a rendered thumbnail and real nozzle-diameter/material/estimate data.
2. **Given** no parts exist yet, **When** an operator instead adds a new part by attaching one already-sliced file (G-code, or a 3MF that already contains sliced G-code), **Then** the system parses it and, exactly like the requires-slicing path, presents the parsed result for review before anything is saved, with the name/tags fields available to fill in throughout; confirming (once a name has been entered) stores the file as-is along with its extracted thumbnail and parsed nozzle diameter/material/estimates.
3. **Given** an operator is adding a part whose file requires slicing, **When** they don't specify a Filament, **Then** the add is rejected — a Filament (generic or specific) must always be supplied for a file that needs slicing.
4. **Given** the farm has no registered printer with a Machine Profile linked yet, **When** an operator tries to add a part whose file requires slicing, **Then** the add is rejected — automatic slicing has no nozzle diameter to target.
5. **Given** an operator is adding a part, **When** its file cannot be successfully parsed or sliced for any reason, **Then** the add is rejected outright — no part is saved in an incomplete or placeholder state, and no review step is ever reached.

### User Story 2 - Automatically derive a part's data via in-app slicing (Priority: P1)

As a print farm operator, I want the system to automatically slice my part's file when it needs slicing (STL, or a 3MF that isn't already sliced) — targeting the material I specify and whichever nozzle diameter is most common across my fleet — so I get real nozzle-diameter/material/estimate data and a thumbnail without manually pre-slicing it myself, configuring anything up front, or the system needing to keep a separate sliced-output file around.

**Why this priority**: This is the headline capability this phase folds in (merging the former Phase 23 — In-app slicing) specifically so every part in the catalog carries real, usable data — without it, adding a part from a raw model would need a manual round-trip through an external slicer first. It's ranked alongside Story 1 because together they're this phase's minimum demoable capability: add a file, get a fully-described part.

**Independent Test**: Given a part is being added with a file requiring slicing and a Filament specified, and the farm has at least one registered printer with a Machine Profile linked, can be tested by confirming the system automatically invokes the configured slicer engine against the farm's most common linked nozzle diameter, that a successful slice lands in a reviewable "ready for review" state showing the rendered thumbnail, parsed estimated print time/weight, and derived nozzle-diameter/material data, and that the part only actually appears in the catalog once the operator confirms it — with no separate sliced-output file ever created, and confirming that a slicing failure rejects the operation entirely rather than saving anything incomplete.

**Acceptance Scenarios**:

1. **Given** an organization has not yet configured a default slicer engine, **When** a part's file requires slicing, **Then** the system uses a sensible built-in default engine (OrcaSlicer) for automatic slicing.
2. **Given** a Filament is specified and the farm has printers with a Machine Profile linked, **When** a part's file requires slicing, **Then** the system automatically invokes the configured engine to slice it against that material and the farm's most common linked nozzle diameter, and once slicing succeeds presents the resulting nozzle diameter, generic material type, estimated print time/weight, and a rendered thumbnail to the operator for review — the slicer's toolpath output itself is discarded, and the part's file remains exactly as uploaded.
3. **Given** the farm's printers-with-a-linked-Machine-Profile are split across two different nozzle diameters, **When** automatic slicing runs, **Then** it targets whichever nozzle diameter the most of those printers currently have, without asking the operator to choose; a printer with no Machine Profile linked is simply not counted.
4. **Given** an operator wants a specific part sliced with a different engine than the organization default, **When** they choose an override engine for that part, **Then** only that part's automatic slice uses the override, without changing the organization-wide default.
5. **Given** the configured slicer engine fails or times out slicing a part's file (e.g. non-manifold geometry), **When** that happens, **Then** the add or replace operation is rejected entirely — the failure is surfaced clearly, and no part (or, for a replacement, no changed data) is saved, with nothing left in a pending review state either.
6. **Given** automatic slicing is in progress for an add or replace request, **When** an operator checks on it, **Then** the system shows a clear in-progress state; once slicing succeeds, the state instead becomes "ready for review" rather than immediately visible in the catalog.
7. **Given** a slice has reached the "ready for review" state, **When** the operator reviews the derived nozzle diameter/material/estimates/thumbnail, **Then** they may optionally attach or change a narrower Filament Profile/color-variant override for the resulting single filament requirement and then confirm, which creates the part (or applies the replacement) immediately from the already-derived data; **or** they may discard the reviewed result instead, in which case nothing is saved and the part (or its prior file/data, for a replace) is exactly as if the slice had never run.

### User Story 3 - Manually provide an already-sliced file (Priority: P1)

As a print farm operator, I want to directly provide an already-sliced file for a part — one I sliced myself externally, or one downloaded pre-sliced with no original model available — so I'm not limited to whatever in-app slicing produces, and the file itself is retained since I already have the real sliced output in hand.

**Why this priority**: Keeps the catalog useful for operators with existing tuned external slicer profiles or pre-sliced files with no original model behind them. Ranked alongside Stories 1–2 since, together, they're what makes every part in the catalog fully described.

**Independent Test**: Can be fully tested by adding or replacing a part's file with an already-sliced file, confirming the system parses its nozzle diameter, generic material type(s), and estimates directly from it and extracts its embedded thumbnail, presents that result for review exactly like a requires-slicing add/replace would, and — once confirmed — stores the file as-is; rejecting the operation instead (with no review step ever reached) if any of that can't be parsed.

**Acceptance Scenarios**:

1. **Given** an operator uploads an already-sliced file (G-code, 3MF, or brand-specific bundle) for a new or existing part, **When** its nozzle diameter, material type, and estimates can all be parsed successfully, **Then** the parsed result is presented for review the same way a slicer-derived result would be, and once confirmed the file is stored as-is (unlike an automatic slice, nothing is discarded here) with that parsed data and an extracted thumbnail.
2. **Given** an already-sliced file was sliced for PETG with a single material, **When** it becomes the part's file with no further narrowing, **Then** the system parses one filament requirement carrying "PETG" as its generic material type, matching any PETG spool/filament by default.
3. **Given** an already-sliced file uses AMS-style multi-color mapping across several slots, **When** an operator adds it, **Then** the system parses one filament requirement per detected slot (each with its own generic material type), and the operator can independently link the specific filament profile/color-variant each slot's mapping corresponds to, narrowing that slot's match beyond its generic material type without affecting the others.
4. **Given** an already-sliced file in a format or state the system cannot fully parse (missing nozzle diameter, material type, or estimate), **When** an operator tries to add or replace with it, **Then** the operation is rejected — there is no manual-entry fallback for any of these values.
5. **Given** a part needs to run on a different nozzle-diameter target than its current file targets, **When** an operator wants both available at once, **Then** they create a separate Part record for the other target — replacing the existing part's file would discard the current one rather than keep both.

### User Story 4 - Replace a part's file (Priority: P2)

As a print farm operator, I want to upload a new file for an existing part, so I can fix or improve its design, or swap in a different result, without recreating the part or losing its name, tags, and other details — and without ever leaving the part in a broken state if the new file doesn't work out.

**Why this priority**: A real maintenance need once a catalog is in active use, but only matters after parts already exist (Story 1), so it's ranked after the core catalog stories. There's no staleness-tracking or multi-file complexity here — replacing is the whole operation, and it either fully succeeds or changes nothing.

**Independent Test**: Can be tested by uploading a replacement file for a part that already has tags and other details set, confirming the part keeps its identity and tags while its file, thumbnail, and derived data update to reflect the new one — and separately, by attempting a replacement with a file that fails to process, confirming the part's original file and data are completely unchanged.

**Acceptance Scenarios**:

1. **Given** a part with an existing file, **When** an operator uploads a replacement file (of either kind) that processes successfully and the operator confirms the reviewed result, **Then** the part's file, thumbnail, and derived data are all replaced while its name and tags remain unchanged.
2. **Given** a part with an existing file, **When** an operator uploads a replacement file that fails to parse or slice, **Then** the replacement is rejected, and the part's original file, thumbnail, and derived data remain exactly as they were — the same outcome as if the operator had discarded a reviewed-but-unwanted result instead.

---

### User Story 5 - Organize the catalog with tags (Priority: P3)

As a print farm operator with a growing catalog, I want to tag parts by category or product line, so I can filter down to the parts I care about instead of scrolling a flat list.

**Why this priority**: Pure organizational convenience — valuable as the catalog grows, but the catalog is fully usable without it, so it's ranked last.

**Independent Test**: Can be tested by tagging several parts with different tag values and confirming the catalog can be filtered down to just the parts sharing a given tag.

**Acceptance Scenarios**:

1. **Given** parts exist with no tags, **When** an operator adds one or more tags to a part, **Then** those tags appear on the part and are available for filtering.
2. **Given** parts tagged with different values, **When** an operator filters the catalog by a tag, **Then** only parts carrying that tag are shown.

### Edge Cases

- What happens when an operator uploads a file that isn't STL, 3MF, or G-code at all? The system should reject the upload and state that only those formats are accepted.
- What happens when an uploaded 3MF's sliced/unsliced status can't be reliably determined from its own metadata? The system should treat it as requiring slicing (the safer default) and attempt automatic in-app slicing; if that also fails, the add/replace is rejected (FR-006).
- What happens when an uploaded 3MF bundles multiple plates/objects internally? The system treats the whole file as one indivisible file belonging to one part, and uses only the first plate's image for the thumbnail — it does not detect, split, or warn about multi-plate content; an accepted limitation, not solved in this phase.
- What happens when an operator adds an already-sliced file whose metadata has no parseable nozzle diameter, material type, or estimate? The add or replace is rejected — there is no manual-entry fallback for any of these values.
- What happens when the configured slicer engine's CLI process crashes, times out, or fails on unsupported/non-manifold geometry during automatic in-app slicing? The add or replace is rejected entirely; the failure is surfaced clearly (not silently swallowed), and — for a replace — the part's existing file and data are left completely unchanged.
- What happens when a file requires slicing and no Filament was specified? The add or replace is rejected — a Filament must always be supplied for a file that needs slicing; there is no fallback default.
- What happens when a file requires slicing but no registered printer has a Machine Profile linked yet? The add or replace is rejected — automatic slicing has nothing to target until at least one printer has one linked.
- What happens when automatic in-app slicing is still running for an add or replace request? The system shows a clear in-progress state; nothing new is visible in the catalog until slicing succeeds *and* the operator confirms the reviewed result.
- Does an already-sliced file's add/replace show the same in-progress state? Yes — it goes through the identical processing → ready-for-review step, it simply resolves near-instantly in practice since parsing embedded metadata needs no external process; an operator may still briefly see a processing indicator before the review step appears.
- What happens if an operator tries to confirm/save a new part before processing has reached "ready for review," or before entering a name? The confirm action is unavailable until both conditions are met — there is no way to force-save early or leave the name blank; the operator can still freely edit the name/tags while waiting, just not submit them, until processing succeeds.
- What happens when a slice reaches "ready for review" but the operator discards it instead of confirming? Nothing is saved — for an add, no part is created; for a replace, the part's existing file and data remain exactly as they were, identical to a slicing failure's outcome except the slice itself succeeded.
- What happens when a Filament Profile/color-variant an operator used to narrow one of a part's filament requirements is later deleted from the Phase 2/3 catalog? That requirement's narrowing reference becomes unresolved and is surfaced as such, but it (and the part as a whole) continues matching on its parsed generic material type and the part's nozzle diameter alone — the other requirements on the same part are unaffected.
- What happens when an operator deletes a part? Its file and all derived data are deleted with it, since nothing in this phase (no Job entity yet) references a part's data independently of the part itself.
- What happens when an operator tries to add a part with no file at all? The system rejects it — a part must have exactly one file to exist.
- What happens when a thumbnail cannot be derived from a part's file (e.g. no embedded preview image present)? The part is still saved, just without a thumbnail — this never blocks saving, unlike the part's nozzle-diameter/material/estimate data.
- What happens when two operators upload a replacement file for the same part at the same time? The system applies one replacement and rejects the conflicting concurrent one rather than corrupt the part's file or derived data.
- What happens when an operator wants the same design available for two different nozzle-diameter targets simultaneously? Not supported on a single Part — they must create a separate Part record for each target they want to keep at once.
- What happens when the farm's registered printers are evenly split between two nozzle diameters (no single most-common value)? The system picks one deterministically (e.g. the smaller diameter, or whichever a stable tiebreak rule selects) rather than failing or asking the operator — the exact tiebreak rule is a planning-level detail.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST allow operators to add a part with a name and exactly one file (STL, 3MF, or G-code). A thumbnail image is automatically derived from the file (FR-014) rather than manually supplied. Attaching the file (and, when required, a Filament — FR-002) begins processing immediately; the name (along with tags, FR-015) MAY be entered or changed at any point while processing runs and is only actually required at the confirm/save step (FR-009a/FR-009b), not before processing can start.
- **FR-002**: System MUST require an operator to specify a Filament (Phase 2/3 — either a generic material match, e.g. "Any PETG," or a specific filament variant) whenever the part's file requires slicing, since automatic in-app slicing (FR-005) needs a material target to run; there is no organization-level default material to fall back on. This is otherwise optional for a file that does not require slicing, since that file's own material is parsed directly from it (FR-012).
- **FR-003**: System MUST determine, for the file attached to a part, whether it requires slicing: an STL file MUST always be treated as requiring slicing, a G-code file MUST always be treated as not requiring slicing, and a 3MF file's status MUST be determined from its own embedded metadata (whether it already contains sliced G-code/toolpath data).
- **FR-004**: System MUST treat every file upload for an existing part as a direct replacement of its current file — a part holds exactly one file at any time, never more. If the new file fails to process (FR-006), the replacement MUST be rejected and the part's existing file and derived data MUST remain completely unchanged.
- **FR-005**: System MUST automatically invoke a headless slicer engine against a part's file whenever it requires slicing (on initial add or after a replacement), targeting the specified Filament (FR-002) and the nozzle diameter most common among the farm's currently-registered printers (FR-005a) — successfully deriving nozzle diameter, generic material type, estimated print time, estimated filament weight, and a rendered thumbnail. A successful slice's derived data MUST be presented to the operator for review (FR-009a) rather than saved directly. The slicer's toolpath output itself MUST NOT be persisted, and the part's file MUST remain exactly as uploaded.
- **FR-005a**: System MUST determine the nozzle diameter to slice against by reading, for each registered printer that has a Machine Profile (Phase 2) linked, that profile's nozzle size, and selecting whichever nozzle diameter is most common among those printers — with no operator input and no organization-level configuration involved. A printer with no Machine Profile linked does not count toward this determination.
- **FR-005b**: System MUST allow an operator to link a registered printer to a Machine Profile (Phase 2) at any time after the printer is created — this link is optional at printer-creation time (a matching profile may not have been imported yet) but is what makes that printer count toward FR-005a's nozzle-diameter determination.
- **FR-006**: System MUST reject an add or replace operation outright — never saving a part or updated data in an incomplete or placeholder state — whenever: (a) the file requires slicing and no Filament was specified, (b) the file requires slicing and no registered printer has a Machine Profile linked (so no nozzle diameter can be determined), (c) automatic in-app slicing fails (engine error, timeout, unsupported/non-manifold geometry), or (d) an already-sliced file's nozzle diameter, material type, or estimate cannot be parsed. There is no manual-entry fallback for any of these values.
- **FR-007**: System MUST allow an operator to configure, at the organization level, only a default slicer engine (OrcaSlicer or Bambu Studio) used for automatic in-app slicing whenever a part-specific override isn't given — no other slicing-target setting is organization-configurable.
- **FR-008**: System MUST allow an operator to override the slicer engine for one specific part's automatic slice, without altering the organization-wide default used elsewhere.
- **FR-009**: System MUST process every add/replace request — whether the file requires slicing or is already sliced — as an asynchronous background operation: the request MUST NOT block on the result, and the system MUST surface a clear in-progress ("processing") state while it runs. This applies uniformly regardless of file type; an already-sliced file typically resolves near-instantly in practice (parsing embedded metadata needs no external process), but goes through the identical shape as a file requiring slicing rather than a separate synchronous path.
- **FR-009a**: System MUST hold every successfully-processed result — however it was produced, by parsing an already-sliced file's own metadata or by an in-app slice — in a "ready for review" state, presenting the derived nozzle diameter, generic material type(s), estimated print time/weight, and thumbnail, rather than saving it directly. The operator MUST be able to (a) optionally attach or change a narrower Filament Profile/color-variant override for any one of the resulting filament requirement(s) (FR-012a) and then confirm, which saves the part (creating it, or applying the replacement) immediately from the already-derived data with no further processing delay, or (b) discard the reviewed result, in which case nothing is saved — for an add, no part is created; for a replace, the part's existing file and data are unaffected. Neither path allows editing the derived nozzle diameter, material type, or estimate values themselves (FR-006/FR-013 — those remain fully derived, never hand-entered).
- **FR-009b**: System MUST allow an operator to enter or change a new part's name and tags at any point while its file is processing, concurrently with FR-009's in-progress state — these are not gated behind processing completion. The confirm action (FR-009a) MUST be unavailable (e.g. a disabled Save control) until both conditions hold: processing has reached "ready for review," and, for a new part, a name has been entered; confirming submits the name/tags together with any narrower filament overrides in the same action. Replacing an existing part's file follows the identical shape, without name/tags (FR-004 — unaffected by a replace).
- **FR-010**: System MUST implement in-app slicing — engine invocation given a file requiring slicing plus a target material and nozzle diameter, producing nozzle diameter, material type, estimated print time/weight, and a thumbnail — as a capability reusable outside this phase's own automatic-at-upload trigger, so Phase 7 (Jobs) can later invoke it on-demand at job-dispatch time to produce actual sliceable output for a job's specific target printer, without rebuilding the slicing integration. This phase itself builds only the automatic-at-upload trigger (FR-005) — no job-dispatch-time trigger exists yet, since no Job entity does.
- **FR-011**: System MUST parse nozzle diameter directly from a part's file when that file does not require slicing, and store it as the part's machine-compatibility requirement, matching any printer sharing that value. There is no concept of linking a part to a specific Machine Profile record, and no filament-diameter matching in this phase.
- **FR-012**: System MUST parse the generic material type (e.g. "PETG", "PLA") directly from a part's file when that file does not require slicing, producing one filament requirement per distinct material/color mapping the file's own embedded metadata declares (a single requirement for a single-material file; one per detected slot for an AMS-style multi-color mapping), each matching any spool/filament of its generic type by default. A file requiring slicing always produces exactly one filament requirement, since in-app slicing targets exactly one operator-specified Filament (FR-002) — true multi-material in-app slicing (assigning different materials to different regions of one model) is out of scope for this phase.
- **FR-012a**: System MUST allow an operator to optionally narrow any one of a part's filament requirements to a specific Filament Profile (Phase 2) or Filament catalog color-variant (Phase 3), overriding that requirement's generic-type default when an exact brand/color match matters (e.g. one slot of a multi-color mapping baked into the file) — independently of any other requirement on the same part.
- **FR-013**: System MUST derive estimated print time and filament weight for every part — parsed directly from its file when that file does not require slicing, or from the automatic in-app slice when it does — as a required condition of saving the part (FR-006); there is no manual-estimate fallback.
- **FR-014**: System MUST automatically derive a part's thumbnail image from its file: for a file requiring slicing, by rendering a preview of the model as part of the in-app slicing pass; for an already-sliced file (G-code, or a 3MF that already contains one), by extracting its embedded preview thumbnail image; for a 3MF bundling multiple plates, using only the first plate's image. A derived thumbnail MUST be normalized to a single standard image format so no per-part image-format tracking is needed.
- **FR-014a**: Failure to derive a thumbnail MUST NOT block adding or replacing a part — a part MAY exist with no thumbnail, unlike its nozzle-diameter/material/estimate data, which MUST be successfully derived (FR-006).
- **FR-015**: System MUST allow operators to tag parts with one or more reusable tag values (category, product line, etc.) and filter the catalog by tag.
- **FR-016**: System MUST allow a part to be added, browsed, tagged, and have its file replaced, with no live printer connection — catalog and slicing operations in this phase never require a live printer connection, though FR-005a does require read access to the printer catalog's Printer-to-Machine-Profile links.
- **FR-017**: System MUST record part creation, file replacements (automatic and manual), a discarded reviewed slice, and organization slicer-engine default changes in the activity log, including who/what made the change and when.
- **FR-018**: System MUST reject adding a part with no file.

### Key Entities

- **Part**: A reusable catalog entry representing something an operator prints repeatedly, saved only once fully described. Key attributes: name, an automatically-derived thumbnail image (may be absent if derivation wasn't possible), tags, exactly one File, one or more Filament Requirements (see below), and always-complete derived print data — nozzle diameter and estimated print time/filament weight. This derived data comes either from directly parsing the File when it's already sliced, or from an in-app slicing pass over the File when it isn't (subject to operator review/confirmation for the latter, FR-009a); either way it must succeed before the Part can be saved — there is no partial, pending, or manually-estimated state, and no filament-diameter field. Distinct from a Job (Phase 7), which doesn't exist yet, and from an Assembly (Phase 6), which is how multiple Parts get combined — a Part itself never holds more than one file's worth of content, and never links to a Machine Profile.
- **Filament Requirement**: One of a Part's one-or-more material needs — a generic material-type requirement (e.g. "PETG") plus an optional narrower override to a specific Filament Profile/color-variant. An already-sliced file with a single material produces exactly one; one with an AMS-style multi-color mapping produces one per detected slot, each independently narrowable. A file requiring slicing always produces exactly one, targeting the single Filament (Phase 2/3) the operator specified as the in-app slicing target.
- **File**: The single file attached to a Part — STL, 3MF, G-code, or a brand-specific bundle — always persisted exactly as uploaded. Determined, at the time it's uploaded, to either **require slicing** (an STL, or a 3MF without embedded sliced G-code) or **not require slicing** (a G-code file, or a 3MF that already contains sliced G-code/toolpath data). Uploading a new file for a part always replaces the current one — there is never more than one at a time, and a failed replacement leaves the existing file and data completely untouched.
- **Tag**: A reusable label (category, product line, etc.) an operator can apply to any number of Parts to organize and filter the catalog.
- **Slicing Defaults (Organization Setting)**: An organization-level configuration naming only the default headless slicer engine (OrcaSlicer or Bambu Studio) used for automatic in-app slicing whenever a part doesn't override it. A part-specific slice request may override the engine for that request only, without changing the stored organization default. Holds no nozzle-diameter, filament-diameter, or material configuration — those are either auto-detected (nozzle diameter, from the printer catalog) or explicitly supplied per part (material).
- **Printer ↔ Machine Profile link**: This phase wires the previously-deferred link between a fleet `Printer` (Phase 1) and a Machine Profile (Phase 2) — the linkage Phase 1's own dependency notes earmarked for "whichever later phase actually consumes it." The link is optional per printer (a matching Machine Profile might not be imported yet), set independently of printer creation. A printer with one linked is treated as a "real fleet member" for FR-005a's nozzle-diameter auto-detection; a printer without one simply doesn't count toward it.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An operator can add a new part with just its file and a Filament (if the file needs slicing) in under 2 minutes, with thumbnail, nozzle-diameter/material data, and estimate all derived automatically — no manual data entry, and no organization configuration, required beforehand.
- **SC-002**: An operator can add or replace a part's file with an already-sliced one and have it fully described (parsed data + thumbnail) in under 1 minute.
- **SC-003**: 100% of parts that exist in the catalog have complete, accurate nozzle-diameter/material/estimate data — since a part is never saved without it.
- **SC-004**: A part's derived nozzle-diameter/generic-material match is broad by construction — any printer and any spool/filament sharing those values qualifies, with zero duplicate parts needed solely because two printers share a nozzle diameter, or two spools share a generic material.
- **SC-005**: An operator can filter a catalog of 500+ parts down to a relevant subset by tag in under 10 seconds.
- **SC-006**: At least 90% of files requiring slicing, added with a Filament specified and at least one printer registered, slice successfully on the first attempt — the remainder are rejected clearly for genuinely unsliceable geometry rather than saved incomplete.
- **SC-007**: An automatic in-app slicing failure never leaves a partially-created or corrupted part — 100% of failed slices result in a clean rejection (or, for a replace, no change at all) with nothing incomplete ever saved.
- **SC-008**: A part created directly from an already-sliced file becomes fully usable exactly as immediately as one produced via automatic in-app slicing — no functional gap between the two paths.
- **SC-009**: At least 90% of successfully-saved parts have a real, non-blank thumbnail automatically derived from their file, with no manual image upload ever required.

## Assumptions

- **A Part holds exactly one File, never a collection.** There is no "source model" concept and no notion of multiple already-sliced variants coexisting on the same Part (e.g. one per nozzle-diameter target) — Assembly (Phase 6) is the mechanism for combining multiple distinct parts, so a Part itself stays deliberately atomic. Running the same design against more than one nozzle-diameter/material combination at once requires separate Part records.
- **A 3MF that bundles multiple plates/objects internally is treated as one indivisible file belonging to one Part**, using only the first plate's image for the thumbnail. The system does not attempt to detect, split, warn about, or otherwise handle multi-plate 3MF content beyond that — an accepted, unaddressed limitation for this phase.
- **A part is never saved in an incomplete state.** Nozzle diameter, generic material type (per filament requirement), and an estimated print time/weight are always successfully derived (via direct parsing or a successful in-app slice) before an add or replace operation completes; any failure (unparseable file, no Filament specified, no known printer nozzle diameter, slicer error) rejects the whole operation rather than saving a partial result. There is no manual numeric entry anywhere for these values — not even at the review/confirm step a requires-slicing add/replace now passes through (FR-009a): review/confirm gates *whether* a successfully-derived result gets saved and lets the operator attach a narrower filament override, never lets them hand-edit the derived numbers themselves.
- **Every add/replace, regardless of file type, has a "ready for review" state between a successful process (parse or slice) and the part actually being saved.** This applies uniformly to already-sliced and requires-slicing files alike — there is no longer a separate one-step synchronous path for an already-sliced file. Both a G-code/already-sliced-3MF upload and an STL/unsliced-3MF upload go through the identical submit → processing → ready-for-review → confirm/discard shape; only the underlying mechanism differs (reading embedded metadata vs. invoking an external slicer), and only that difference — not the operator-facing flow — determines how long "processing" takes (typically near-instant for an already-sliced file). Reaching "ready for review" is not a partial/incomplete state the way an unprocessed or failed attempt is — it is a fully-derived, complete result that simply hasn't been committed yet, pending an explicit confirm (or discard) from the operator.
- **A Part's filament requirement is a collection, not a single value.** A single-material file (sliced or already-sliced) produces exactly one filament requirement; an already-sliced file with a real AMS-style multi-color mapping produces one requirement per detected slot, each with its own generic material type and independently-optional narrower override. In-app slicing itself still only ever targets one operator-specified Filament per slice (true multi-material *slicing* — different materials for different regions of one model — is out of scope for this phase), so a requires-slicing part always ends up with exactly one requirement even though the data shape supports more.
- **There is no "job-ready" state.** Every part that exists is, by construction, fully valid and usable — there's nothing to flag as not-ready. The only remaining status distinction a part carries is whether its file requires slicing (Phase 7 will need to slice it again for real toolpath data at job-dispatch time, since nothing sliceable is persisted) or was already sliced on upload (its stored file can be sent to a printer directly).
- **A part's thumbnail is automatically derived from its file, never manually uploaded.** For a file requiring slicing, it's rendered from the model as part of the in-app slicing pass (e.g. via a slicer CLI's plate-preview export capability). For an already-sliced file, it's extracted from the file's own embedded preview image — G-code embedding a base64 preview in comments, and Bambu-style `.gcode.3mf` embedding one in its metadata, are both standard, widely-supported slicer/firmware conventions (used for printer on-device screens), so this is reliably available for already-sliced files too. Deriving a thumbnail is best-effort only — unlike nozzle-diameter/material/estimate data, its failure never blocks saving the part. **Whatever source format a derived/extracted thumbnail arrives in, the system normalizes it to one standard image format at save time** — a thumbnail is always an image, so there is no need to separately track each part's thumbnail's original format/content-type.
- **There is no concept of linking a part to a specific Machine Profile.** A part's machine compatibility is expressed purely through its derived nozzle diameter. The optional narrower link to a specific Filament Profile/color-variant (for exact brand/color matching) is unaffected by this and still supported.
- **Filament-diameter matching is dropped from this phase entirely.** The modern desktop-printer market this project targets is virtually uniform at 1.75mm, and printer telemetry doesn't naturally expose it, so tracking it isn't worth the added printer-catalog work. Only nozzle diameter and generic material type gate compatibility.
- **There is no organization-configured default material.** A Filament (generic or a specific variant) is a hard, per-part requirement whenever a file needs slicing — supplied by the operator in the same add/replace request, never defaulted at the organization level.
- **Nozzle diameter for automatic slicing is auto-detected from the farm's registered printers, not configured.** Specifically, the value most common among printers that have a Machine Profile linked is used, with no operator input and no organization-level Settings field for it. **This phase resolves its dependency on the printer catalog (Phase 1) by finally wiring the Printer ↔ Machine Profile link that `docs/FEATURE_PLAN.md`'s own Phase 1 dependency notes already earmarked for "whichever later phase actually consumes it"** — nozzle diameter is read from a printer's linked Machine Profile (Phase 2, which already models nozzle size), not a new duplicate field on `Printer`. The link is optional at printer-creation time (a matching Machine Profile might not be imported yet), so a printer can exist without one; only a printer with one linked counts as a "real fleet member" for this determination (FR-005a/FR-005b). If no registered printer has a Machine Profile linked, automatic slicing — and therefore adding or replacing a part whose file requires slicing — is rejected (FR-006) until at least one does.
- This auto-detected nozzle diameter is purely Phase 4's own slicing-target heuristic. It is explicitly distinct from real job/printer matching at dispatch time (Phase 7), which will depend on which printers and feed-slot materials are actually available at that later moment, not on this phase's one-time slicing choice.
- **Uploading a new file for an existing part is always a direct, destructive replacement, and it either fully succeeds or changes nothing.** There's no staleness flag and no versioned file history; a failed replacement leaves the part's prior file and derived data completely untouched rather than partially updated.
- **A job already queued or printing (Phase 7) is unaffected by a part's file being replaced afterward, by construction of the two phases together rather than anything this phase itself needs to build.** Per `docs/FEATURE_PLAN.md`'s Phase 7 section, a job locks onto a copy/reference of the print-ready content it needs at queue time (whether that's the part's stored already-sliced file, or a fresh on-demand slice Phase 7 itself produced), not onto "whatever the part's file currently is." No FR in this phase exists for this specifically — it's a requirement on Phase 7's own job-locking design, noted here for traceability.
- This phase covers catalog data only — a part and its tags — with no interaction with a live printer connection or an actual print job; those come in Phase 7 (Jobs) and later phases. In-app slicing itself needs no live printer connection either — only the part's file, the specified material, the auto-detected nozzle diameter, and the configured slicer engine/CLI.
- A part's derived print data (nozzle diameter, generic material type) requires no dependency on the Phase 2 profile catalog beyond the Filament itself (already required per FR-002) — it's either parsed straight from an already-sliced file or produced by a slicing pass. Phase 2 (Profiles — machine + filament, imported from slicer bundles, `specs/003-slicer-profile-import`) is only additionally needed for the optional narrower Filament Profile/color-variant override.
- **This phase merges the former Phase 23 — In-app slicing into Phase 4**, since a file requiring slicing carries none of the parseable time/weight/nozzle metadata FR-011/FR-012/FR-013 depend on — only an actual slicing pass produces it. `docs/FEATURE_PLAN.md` is updated accordingly to fold Phase 23's scope into Phase 4 and renumber the former Phase 24 down to Phase 23.
- Every add/replace — in-app slicing or already-sliced-file parsing alike — executes as an asynchronous background operation (per this project's constitutional rule that long-running work never blocks a request thread, and per the unified Processing → Ready for Review shape both paths now share); a successful result reaches a "ready for review" state rather than committing directly, and notifies the operator of that (or of a failure) through the same real-time channel other live updates already use. The part is only actually created/updated once the operator explicitly confirms the reviewed result (FR-009a).
- OrcaSlicer is the built-in default engine when no organization Settings override exists yet, given its open-source (GPLv3) licensing and the broader printer/profile support Phase 2's import flow already relies on.
- A file requiring slicing is assumed to be a clean mesh/project export, not another slicer's fully-baked project file, so it's assumed not to carry another slicer's project-level settings/metadata. The documented OrcaSlicer/Bambu Studio cross-compatibility gaps (one rejecting or partially loading the other's saved project `.3mf`) are therefore not a blocker for feeding it into whichever engine is configured; that risk applies only to a manually-uploaded, already-sliced file produced externally by a specific slicer, which this phase's parsing (FR-011/FR-012/FR-013) treats as metadata to scan rather than a project file to fully reopen.
- Running a headless slicer engine (OrcaSlicer and/or Bambu Studio CLI) is a new external infrastructure/tooling dependency this phase introduces — installed and invoked from the backend — distinct from anything Phase 0–3 needed.
- **3MF requires-slicing/already-sliced disambiguation (FR-003)** is based on the file's own embedded metadata — specifically, whether it contains actual sliced G-code/toolpath data and the slicing-result metadata produced alongside it (e.g. Bambu's `Metadata/slice_info.config`, which only exists in an already-sliced `.gcode.3mf`, versus an unsliced project/mesh 3MF which lacks it). An uploaded STL can never be ambiguous this way (STL has no capacity to embed toolpath data at all), and a plain `.gcode` file is unambiguously always already-sliced (there's no "unsliced" form of a G-code file).
